# Запуск подготовленной разработки в Claude Code

Этот файл — точка входа пользователя. Спецификация и карточки уже подготовлены; реализацию выполняет Claude Code в репозитории, а не обычный чат без доступа к файлам и терминалу.

## Где открыть

- Репозиторий: <https://github.com/BaonixD/BIS-project>.
- Можно открыть существующую локальную папку BIS или клонировать репозиторий в Claude Code Desktop/терминале.
- Выбрать Opus 5.5, если он доступен в аккаунте. При недоступности модель не подменяется без уведомления.
- Для терминального запуска поддерживаемой версией Claude Code: `claude --model claude-opus-5-5` из корня репозитория.
- Для запуска и интеграционных тестов потребуется локальный Docker с работающим daemon. Ключи передаются через локальное окружение, не через Git.

## Промпт для первого запуска

Скопировать в Claude Code целиком:

```text
Выполни подготовленный пакет разработки бэкенда BIS-project.

Прочитай CLAUDE.md, BACKEND_PLAN.md, ORCHESTRATION.md,
docs/MVP_SPEC.md, docs/TASKS.md и текущую карточку docs/tasks/.

Разрешаю реализацию T00–T10 по этой спецификации, локальные ветки,
worktree, коммиты и интеграцию в integration/backend-mvp.
Рабочие допущения из MVP_SPEC используй как стартовые решения;
не спрашивай их заново и не расширяй scope.
Фронтенд, CI, микросервисы и Kafka не добавляй.

Используй Opus 5.5. При доступности делегируй карточки bis-implementer,
а независимое ревью — bis-reviewer. Проверь изоляцию рабочей копии
каждого пишущего исполнителя. При невозможности подагентов исполняй
последовательно и честно отмечай самопроверку.

Для каждого нового поведения сначала тест и содержательный RED,
затем реализация до GREEN и рефакторинг. Проверяй на PostgreSQL/PostGIS.

Начни с первой незавершённой доступной задачи, проверь её зависимости.
После каждой задачи обновляй очередь и отчёт и переходи к следующей.
Не заканчивай работу после одного этапа, если есть доступные задачи.
Не переписывай подготовленный план вместо реализации.

Ключ маршрутизации, Kaspi-ссылку и Google credentials не выдумывай.
Если их нет, реализуй проверяемый адаптер, явно отметь external_pending,
продолжай остальные задачи и отдельно перечисли нужные значения.
Не выдавай mock-запрос за реальную интеграцию.
Google T11 пока оставь отдельным последующим расширением.

Не сливай реализацию в main, не делай push и не создавай PR без команды.
В конце подготовь docs/reports/FINAL.md для ревью Astra:
ветка, SHA, запуск, пройденные проверки и реальные ограничения.
```

## Если сессия прервалась

```text
Продолжи BIS-project по CLAUDE.md и docs/TASKS.md.
Сначала проверь Git, worktree и отчёты docs/reports/.
Сохрани незавершённые изменения. Не начинай законченные задачи заново.
Выполни следующую доступную карточку и продолжай пакет T00–T10.
```

## Что понадобится от владельца позже

- API-ключ выбранного маршрутного сервиса для реальной проверки маршрута в Алматы.
- Ссылка Kaspi Pay. Без неё наличная оплата работает, Kaspi недоступен.
- Google client credentials только при отдельном запуске T11.
- Роли участников, дедлайн и требования преподавателя — для финальной сдачи, без блокировки технической основы.

Обычная Kaspi-ссылка не даёт автоматического подтверждения платежа. В MVP применяется явно описанная ручная сверка, а не вымышленный webhook.

## Передача результата обратно Astra

Открыть ту же рабочую копию с `integration/backend-mvp` или передать доступный commit и написать:

```text
Claude выполнил пакет. Проверь integration/backend-mvp и
docs/reports/FINAL.md, выполни итоговое ревью и проверь готовность бэкенда.
```

При работе на другой машине публикация integration-ветки потребует отдельной команды пользователя. Не считать локальную ветку автоматически доступной на GitHub.
