Исполнимая декомпозиция: [docs/TASKS.md](docs/TASKS.md). Контракты и явно обозначенные рабочие допущения для автономной реализации: [docs/MVP_SPEC.md](docs/MVP_SPEC.md). При уточнении требований эти документы обновляются вместе.

## 2. Цель и границы

К концу семестра подготовить работающий, воспроизводимо запускаемый mini taxi service с пользовательским интерфейсом. На защите показывается готовое приложение, а не отдельный бэкенд. Этот план описывает текущий этап разработки бэкенда, который затем подключается к интерфейсу.

Проект учебный и, вероятнее всего, будет запускаться локально. Требование «как production-ready на бумаге» означает ясную архитектуру, целостность данных, обработку ошибок, контроль доступа, миграции, тесты и документацию. Готовность к реальной коммерческой эксплуатации не заявляется без отдельной проверки.

### Зафиксировано

- Сейчас разрабатывается только бэкенд.
- Основной стек: Python, FastAPI. На текущем этапе по решению владельца от 3 ноября 2026 — SQLite без Docker ([ADR 0001](docs/decisions/0001-sqlite-without-docker.md)); целевой переход на PostgreSQL/PostGIS остаётся возможным.
- Архитектура: модульный монолит, одно серверное приложение и одна основная БД.
- Интерфейс на React будет разрабатываться следующим этапом и нужен для итогового показа. Мобильное приложение остаётся необязательным, если хватит времени. Они не входят в текущую реализацию бэкенда.
- Нужны понятная структура, разделение ответственности, clean code, разумное применение SOLID и DRY.
- Комментариев в коде минимум; сложные причины и ограничения при необходимости объясняются.
- Нужны отдельный Python-скрипт линтинга, корректные миграции и отдельный seed.
- CI не используется. Проверки выполняются локально.

### Не включаем в текущую архитектуру

- Микросервисы, Kafka, Kubernetes, распределённые транзакции.
- Redis, Celery, отдельный брокер и фоновые worker-сервисы без конкретного согласованного требования.
- Облачную инфраструктуру, автоматический деплой и инфраструктуру высокой доступности.
- Дополнительные библиотеки исключительно ради расширения стека.

Любая новая инфраструктурная зависимость должна решать описанную проблему и согласовываться с владельцем проекта.

### Учебный тариф

Предлагаемая базовая модель в рамках поручения пользователя:

- Посадка: **500 ₸**.
- Расстояние по дорожному маршруту: **120 ₸/км**.
- Расчётное время маршрута: **20 ₸/мин**.
- Минимальная стоимость: **800 ₸**.
- Итог округляется до целого тенге по правилу `ROUND_HALF_UP`.

```text
стоимость = округлить(max(800, 500 + 120 × километры + 20 × минуты))
```

Пример: маршрут 10 км и 25 минут стоит `500 + 1200 + 500 = 2200 ₸`.

Это учебные значения, не утверждение о рыночных ценах такси. Расстояние и время берутся из внешнего маршрутного сервиса, расчёт выполняется на сервере. Для простой первой версии предлагаем фиксировать цену при создании заказа и сохранять применённую версию тарифа, исходные метры и секунды. Динамический спрос, платное ожидание, изменение пункта назначения и штрафы за отмену пока не входят в предложенный объём.

## 3. Техническая основа

| Область | Решение |
| --- | --- |
| HTTP API | FastAPI, Pydantic, версионирование через `/api/v1` |
| Данные | SQLite на текущем этапе (ADR 0001); код переносим на PostgreSQL/PostGIS |
| Работа с БД | SQLAlchemy 2.x async, драйвер aiosqlite; asyncpg — при переходе на PostgreSQL |
| Географические данные | longitude/latitude (WGS 84) и haversine в метрах; GeoAlchemy2 — при переходе на PostGIS |
| Миграции | Alembic |
| Конфигурация | Типизированные настройки через pydantic-settings и переменные окружения |
| Зависимости | uv, `pyproject.toml`, сохраняемый в Git `uv.lock` |
| Стиль кода | Ruff: линтинг, импорты и форматирование |
| Типы | mypy для кода приложения |
| Тесты | pytest, HTTPX; один согласованный механизм запуска async-тестов |
| Локальный запуск | `uv run` без Docker (ADR 0001) |

Точные совместимые версии Python, библиотек и образов выбираются при подготовке основы и фиксируются. Плавающие теги `latest` для воспроизводимого запуска не используем. Внешние интеграции, если они понадобятся, получают отдельные клиентские адаптеры.

## 5. Ответственность и зависимости

| Часть | Ответственность |
| --- | --- |
| `main.py` | Создание приложения и подключение API, middleware, обработчиков ошибок и lifespan |
| `api/router.py` | Сборка роутеров и префиксов API |
| `api/exception_handlers.py` | Перевод ошибок приложения в единый формат HTTP-ответов |
| `core/config.py` | Загрузка и проверка настроек |
| `core/lifespan.py` | Открытие и освобождение ресурсов приложения |
| `database/base.py` | Базовый ORM-класс, общие соглашения об именовании ограничений |
| `database/session.py` | Engine, фабрика сессий и управление их временем жизни |
| `database/metadata.py` | Явный сбор ORM-моделей для Alembic |
| `router.py` | HTTP-вход, вызов сценария и HTTP-ответ |
| `schemas.py` | Контракты запросов и ответов, проверка формы данных |
| `service.py` | Бизнес-сценарии функциями модуля, их SQL-запросы и границы транзакций ([ADR 0008](docs/decisions/0008-functional-services.md)) |
| `models.py` | ORM-модели, ограничения и индексы |
| `dependencies.py` | Сборка зависимостей для API |
| `exceptions.py` | Именованные ошибки предметного модуля |
| `scripts/seed.py` | Отдельная команда запуска seed |
| `seeds/` | Демонстрационные наборы данных и логика их наполнения |

Основное направление вызовов: `router → service → database` (ADR 0008: сервисы — функции, отдельного слоя репозиториев нет). Pydantic проверяет форму входных данных, сервис — бизнес-правила, БД — ограничения целостности, включая защиту от конкурентных изменений.

- Сервисы не зависят от HTTP-запроса и не выбрасывают `HTTPException`.
- Функции-запросы не начинают и не коммитят транзакцию; целостной операцией управляет бизнес-функция сервиса.
- Одна бизнес-операция может вызывать несколько функций-запросов внутри общей транзакции.
- Начало и завершение транзакции имеют одного владельца. Учитываем автоматическое начало транзакции SQLAlchemy, чтобы проверки авторизации не создавали конфликт с последующим `begin`.
- Сессии не являются глобальными и не разделяются между одновременно выполняющимися задачами.
- Запросы загружают необходимые данные явно; сериализация ответа не должна незаметно выполнять SQL.
- Межмодульные обращения проходят через обозначенные функции и контракты. Циклические зависимости устраняем на уровне дизайна.
- Отдельные интерфейсы вводим только при реальной пользе.
- Импорт модулей не запускает запросы, миграции или seed.

## 6. Правила кода

- Понятные английские имена сущностей, функций и переменных; единая терминология предметной области.
- Небольшие функции с одной понятной задачей; ранние проверки и ограниченная вложенность.
- Типизация кода приложения. `Any`, `type: ignore` и `noqa` применяются адресно и с причиной.
- SOLID применяется к ответственности, зависимостям и контрактам; количество классов само по себе не является показателем качества.
- DRY применяется к одному и тому же знанию или правилу. Разные правила с похожей реализацией не объединяем преждевременно.
- Комментарии объясняют нетривиальные причины. Не пересказываем очевидные действия кода.
- Docstring нужен там, где уточняет контракт, побочные эффекты или ограничения.
- Доменные схемы остаются внутри модулей; общие `schemas/` содержат только общие контракты.
- Не создаём общий `utils.py` как место для несвязанных функций.
- Ошибки не подавляются без предусмотренного восстановления. Клиент получает предсказуемый код ошибки, разработчик — диагностическую запись.
- В async-коде используем неблокирующий ввод-вывод; блокирующие операции выполняются подходящим способом вне event loop.
- Конфигурация и секреты отделены от кода. `.env` не коммитится, `.env.example` содержит безопасные примеры.

## 7. Данные, безопасность и надёжность

### Данные

- Явные внешние ключи, уникальность и `CHECK`-ограничения там, где они выражают согласованные инварианты.
- Индексы создаются под реальные запросы; пространственные запросы учитывают особенности PostGIS.
- Для координат явно фиксируются система координат, порядок долгота/широта и единицы измерения расстояния.
- Деньги хранятся точно: `Decimal`/`NUMERIC` либо целые минимальные денежные единицы. Валюта и округление фиксируются после опроса.
- Время хранится с часовым поясом, в UTC. Представление для пользователя отделяется от хранения.
- Правила удаления пользователей, водителей и сохранения истории поездок определяются до реализации соответствующих операций.

### Контроль доступа

- Первая версия поддерживает уникальное имя пользователя и пароль. Способ выдачи и хранения сессий/токенов фиксируется в контракте с будущим React-клиентом.
- Google-вход подключается последующим расширением через проверяемый сервером стандартный identity flow. Google-идентификатор связывается с пользователем отдельно от локального пароля; совпадения произвольного email недостаточно для молчаливого объединения аккаунтов. Срок включения Google в сдаваемую версию ещё не определён. Основа: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).
- Пароли, если они используются, хешируются поддерживаемой библиотекой с современным алгоритмом; собственная криптография не пишется.
- Проверяются не только роли, но и права на конкретную поездку или профиль.
- Ответы API и логи не раскрывают пароли, токены, строки подключения и ненужные персональные данные.
- CORS настраивается для согласованных клиентов. Пользовательские поля не передаются напрямую в произвольные обновления ORM.

### Конкурентные действия

После опроса фиксируется таблица допустимых переходов состояния поездки и инициаторов каждого перехода. На уровне БД и транзакций обеспечиваются согласованные ограничения: например, один заказ не может быть одновременно принят двумя водителями.

Для назначения уже согласована последовательная выдача предложений ближайшим доступным водителям. Предложение имеет серверный срок действия 30 секунд. После отказа или истечения срока выбирается следующий кандидат. Принятие просроченного, отменённого или заменённого предложения отклоняется атомарно.

Предложения, их сроки и результаты сохраняются в БД. Перезапуск API не должен превращать временное предложение в бессрочное назначение. Механизм обработки сроков выбирается внутри монолита; для этого не добавляются Kafka, Celery или отдельный worker-сервис. Если нужен фоновый цикл, его состояние восстанавливается из БД и операции защищаются от повторного исполнения.

Для реализации ещё нужно определить смысл «ближайший» — географическое расстояние или время подачи по дорогам, область поиска, критерий свежести координат и завершение поиска при отсутствии кандидатов.

Для конфликтующих операций выбираются условные атомарные обновления, блокировки и/или ограничения БД. Повторные запросы обрабатываются согласно описанному контракту. Одной предварительной проверки в Python недостаточно для защиты от гонок.

### Дорожные маршруты

- Клиент внешнего сервиса отделён от бизнес-логики и возвращает нормализованные расстояние в метрах, время в секундах и геометрию маршрута.
- Провайдер выбирается после проверки покрытия Алматы, условий доступа, лимитов и подходящих сценариев использования. Платный тариф не подключается автоматически.
- У исходящих запросов есть таймауты, предсказуемые ошибки и ограниченные повторы там, где они безопасны.
- При недоступности провайдера API сообщает об этом; прямое расстояние между точками не выдаётся за дорожный маршрут.
- Демонстрация допускает движение симулированного водителя по реальному полученному маршруту.
- Маршрутизация, геокодирование адресов и отображение карты — разные возможности. Требование к поиску адресов уточняется отдельно; backend-провайдер маршрутов не определяет автоматически карту фронтенда.
- Изолированные тесты используют контролируемые ответы адаптера; перед приёмкой интеграции выполняется отдельная проверка реального маршрута в Алматы.

### Наличные и Kaspi по ссылке

Решение владельца от 3 ноября 2026 года — оплата «как в такси» ([ADR 0010](docs/decisions/0010-pay-before-order.md), заменяет поток ADR 0009).

- Жизненный цикл поездки отделён от учёта оплаты. Заказ создаёт запись оплаты в той же транзакции: `cash` — `unpaid`, `kaspi_link` — сразу `paid` (имитация списания).
- Отмена пассажиром или `no_driver` возвращает оплаченный Kaspi (`refunded`, имитация). Наличные после поездки подтверждает назначенный водитель. Сверки нет.
- Ссылка Kaspi — настройка `KASPI_PAYMENT_URL` (хост `pay.kaspi.kz`). Бэкенд отдаёт сумму, валюту и ссылку; фронтенд показывает QR или открывает ссылку на телефоне.
- Не придумываем формат Kaspi deeplink и параметры автоподстановки суммы: покупатель вводит сумму сам.
- Реальных платежей и банковских API нет; система не проверяет, что деньги пришли. `paid` — отметка пассажира, а не подтверждённый платёж.
- Без ссылки Kaspi недоступен клиенту; наличный сценарий остаётся рабочим.

Официальный [Kaspi Гид](https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2098) описывает ссылку конкретной точки продаж: покупатель самостоятельно вводит сумму, а кассир получает уведомление в мобильном POS. API для проверки оплаты конкретной поездки у такой ссылки нет, поэтому автоматическое подтверждение не обещается.

### Эксплуатация на локальной машине

- Структурированные логи, идентификатор запроса и понятные сообщения ошибок.
- Простые проверки жизнеспособности приложения и готовности БД.
- Корректное закрытие подключений при остановке.
- Документированный способ резервного копирования и восстановления локальной БД перед потенциально разрушительными изменениями.
- Отдельный мониторинговый стек не требуется.

## 8. Миграции и seed

### Миграции

1. Все изменения схемы выполняются через Alembic. `create_all()` не заменяет миграции приложения.
2. Начальная схема воспроизводимо создаётся на пустой базе.
3. `env.py` получает полный `target_metadata` без запуска FastAPI.
4. Имена таблиц, индексов и ограничений задаются единообразно.
5. `autogenerate` создаёт заготовку. Проверяем SQL-смысл, переименования, преобразования данных, значения по умолчанию и пространственные индексы.
6. Подключение PostGIS выполняется отдельным документированным шагом подготовки БД с необходимыми правами. Само расширение не удаляется при обычном откате прикладной схемы.
7. Настраиваем Alembic/GeoAlchemy2 для пространственных типов и индексов; служебные таблицы расширения исключаем из сравнения.
8. В общей ветке поддерживается одна вершина миграций. Порядок ревизий согласуется по [ORCHESTRATION.md](ORCHESTRATION.md).
9. Применённые в общей среде ревизии не переписываются. Исправления оформляются следующими ревизиями.
10. Миграции выполняются отдельной командой до запуска обслуживающего запросы приложения, один раз на обновление.
11. Проверяем установку с нуля, обновление с предыдущей согласованной версии и сохранность существующих данных.
12. Обратимые изменения имеют проверяемый `downgrade`. Для необратимых изменений описываем потери и восстановление; наличие функции `downgrade` не считается гарантией возврата данных.
13. `alembic check` используется как дополнительная проверка расхождений и имеет ограничения того же механизма сравнения, что `autogenerate`.

### Seed

- Seed запускается явно через `scripts/seed.py`, отдельно от `main.py`, lifespan и миграций схемы.
- Повторный запуск не создаёт дубликаты и не перезаписывает пользовательские изменения без явного назначения команды.
- Демонстрационные данные имеют узнаваемые стабильные идентификаторы или ключи.
- Команда проверяет целевое окружение и не очищает БД по умолчанию.
- Обязательные справочники, от которых зависит работа приложения, отделяются от demo seed и получают собственный документированный способ доставки.
- Тесты используют свои фабрики/фикстуры, а не зависят от ручного запуска демонстрационного seed.

## 9. Локальные проверки без CI

`scripts/lint.py` — небольшой Python-скрипт запуска Ruff. Он проверяет код, возвращает ненулевой код при ошибке и не исправляет файлы автоматически. Настройки инструментов находятся в `pyproject.toml`.

Целевые команды, которые станут доступны после настройки проекта:

```bash
uv run python scripts/lint.py
uv run mypy src/taxi_service
uv run pytest
uv run alembic upgrade head
uv run alembic check
```

Внутри скрипта линтинга выполняются `ruff check .` и `ruff format --check .`. Явное исправление стиля запускается отдельно:

```bash
uv run ruff check --fix .
uv run ruff format .
```

Операции проверки миграций выполняются на явно выбранной тестовой БД. Тесты не должны использовать рабочую демонстрационную БД. GitHub Actions, другие CI-пайплайны и обязательные Git hooks не настраиваются.

### Уровни тестирования

| Уровень | Что проверяем |
| --- | --- |
| Unit | Расчёты, правила состояний и другие изолируемые бизнес-правила |
| Integration | Реальные SQL-запросы, ограничения, транзакции и PostGIS |
| API | Контракты, валидацию, аутентификацию и доступ к объектам |
| Migrations | Создание схемы, обновление существующей БД и обратимость заявленных операций |
| Сквозной сценарий | Полную согласованную поездку через публичный API |

Интеграционные тесты на текущем этапе работают на файловой SQLite-БД с независимыми соединениями (ADR 0001); поведение на PostgreSQL/PostGIS перепроверяется при переходе. Внешние платные или недетерминированные сервисы в обычных тестах подменяются на границе клиента.

Приоритет: конкурентное принятие заказа, конфликт отмены и принятия, истечение 30 секунд и поздний ответ водителя, восстановление предложений после перезапуска, повторные запросы, недопустимые переходы, чужие объекты, ошибки маршрутизации, точность тарифа, оплата только пассажиром завершённой поездки, географические границы и миграции. Тесты формируются по требованиям; процент покрытия сам по себе не является критерием готовности.

## 10. Порядок реализации

Этапы описывают будущую работу. Сроки и функциональный состав уточняются после опроса.

| Этап | Результат | Условие завершения |
| --- | --- | --- |
| 0. Опрос и спецификация | Роли, сценарии, границы MVP, таблица состояний, критерии защиты | Критичные для первого этапа вопросы раздела 13 закрыты; остальные имеют явный статус |
| 1. Основа проекта | Установка зависимостей, структура, настройки, Docker, логи и локальные проверки | Другой участник воспроизводит запуск по README |
| 2. Данные | Модели, ограничения, PostGIS, Alembic, отдельный seed | Пустая БД разворачивается; миграции проверены; seed повторяем |
| 3. Идентификация и участники | Username/password, профили и права; точка расширения для Google | Проверены успешные сценарии и запреты доступа |
| 4. Основной сценарий поездки | Дорожный маршрут, расчёт цены, создание, предложения водителям с таймаутом 30 секунд и дальнейший жизненный цикл | Сценарий проходит через API; конфликтующие действия не нарушают инварианты |
| 5. Завершение бэкенда MVP | История, учёт наличной оплаты, контракт Kaspi по предоставленной ссылке и согласованные дополнительные функции | Выполнены критерии приёмки; внешние ограничения явно обозначены |
| 6. Передача для интерфейса | Документация API, демонстрационные данные, воспроизводимый сквозной сценарий | Другой участник может подключать клиент без чтения внутренних деталей бэкенда |

После этого отдельный план фронтенда доводит сервис до готового приложения для защиты. Google-вход реализуется последующим расширением; его обязательность к сдаче ещё уточняется. Отдельная демонстрация Swagger не заменяет финальное приложение с интерфейсом.

Для каждой функциональной задачи действует **test-first: RED → GREEN → REFACTOR**. Сначала пишется тест требуемого поведения и проверяется ожидаемое падение, затем реализуется минимально достаточное поведение, после чего код улучшается при зелёных тестах. Это цикл для отдельных сценариев, а не написание всех тестов проекта заранее. Сбой окружения не считается содержательным RED. Для ошибки сначала создаётся воспроизводящий её regression-тест.

Тесты, документация API и миграции входят в соответствующую функциональную задачу. Они не откладываются целиком до последнего этапа. Для инфраструктурного bootstrap и документации используются соответствующие smoke-проверки; искусственные unit-тесты конфигурации ради TDD не нужны. Линтинг и проверка типов доступны начиная с основы проекта.

## 11. Критерии готовности

### Для отдельной задачи

- Выполнены критерии карточки задачи.
- Для изменения поведения зафиксированы RED/GREEN: команда, ожидаемая причина падения и успешный повторный запуск.
- Соблюдены границы ответственности и существующие контракты.
- Добавлены необходимые проверки поведения, включая существенные ошибки и ограничения.
- Локальный линтинг, проверка типов и относящиеся к задаче тесты проходят.
- При изменении схемы есть проверенная миграция.
- Изменение подтверждено оркестратором на интегрированном результате.
- Нет секретов, случайных зависимостей, отладочного мусора и посторонних изменений.

### Для бэкенда MVP

- Есть согласованный полный сценарий поездки, доступный через API.
- Назначение учитывает принятие, отказ, 30-секундный таймаут и переход к следующему кандидату.
- Реальный дорожный маршрут в Алматы получен через выбранного провайдера, учебный тариф рассчитывается на сервере в KZT.
- Проект запускается локально по README на подготовленной машине другого участника.
- Конфигурация, миграции и демонстрационные данные воспроизводимы.
- Проверены права, состояния, повторные запросы и существенные конкурентные конфликты.
- Swagger/OpenAPI описывает входные данные, ответы и основные ошибки.
- Упрощения маршрутизации, расчёта цены, оплаты и движения водителя явно документированы, если они приняты.
- Все обязательные требования преподавателя выполнены.
- Команда может объяснить схему данных, разделение ответственности и ключевые решения.

Для всего учебного проекта дополнительно нужен готовый пользовательский интерфейс и проверка сценариев через него. Готовность бэкенда и готовность всей сдаваемой версии фиксируются отдельно.
