## Реализованное поведение

- Схема: `ride_offers` (статусы, `expires_at`, `responded_at`, `search_started_at`), частичные уникальные индексы «одно pending на поездку» и «одно pending на водителя», `UNIQUE(ride_id, driver_id, search_started_at)`; в `rides` окно поиска `search_started_at` / `search_deadline` (+180 с), индексы истории `rides(passenger_id, created_at, id)` и `rides(driver_id, created_at, id)`.
- Кандидаты: approved, online, с машиной, координата ≤ 60 с, ≤ 5 км (haversine), без активной поездки и без pending; исключены водители, спрошенные в текущем поиске, и освободившие эту поездку. Отказавшиеся в прошлом поиске после release снова кандидаты (MVP_SPEC §6).
- Шаг поиска (одна транзакция, блокировки rides → ride_offers): просроченные pending (`now >= expires_at`) → expired; поездка не в searching → отзыв pending; бюджет 180 с исчерпан или нет кандидатов → `no_driver`; иначе предложение ближайшему на 30 с. Проигранная гонка уникального индекса — следующий кандидат, другие ошибки поднимаются.
- Поиск стартует после коммита создания поездки; при сбое первого шага ответ 201 `searching`, поездку подхватывает цикл. Повтор идемпотентного создания поиск не запускает.
- API: `GET /api/v1/drivers/me/offers`, `POST /api/v1/ride-offers/{id}/accept|reject` (только адресат, CSRF). Accept атомарный (`now < expires_at` в транзакции); поздний → 409 `offer_expired` и следующий кандидат; повтор — прежний результат; занятый водитель → 409 `driver_busy`; чужое → 404 `offer_not_found`.
- Водитель offline или потерял допуск → его pending `revoked`.
- Фоновый цикл в lifespan (`DISPATCH_INTERVAL_S=1.0`): read-проверка, затем транзакция на каждую поездку; ограниченное логирование серии сбоев; остановка до закрытия engine. Состояние только в БД — после перезапуска восстанавливается.
- Настройки `OFFER_TTL_S=30`, `SEARCH_BUDGET_S=180`, `DISPATCH_INTERVAL_S`, `DISPATCH_LOOP_ENABLED`. ADR 0006, README «Назначение водителя».

## Решения для владельца

- Бюджет 180 с проверяется перед новым предложением: последнее предложение живёт полные 30 с, назначение возможно до ~210 с от начала поиска.

## Ограничения

PostgreSQL проверен только компиляцией SQL; конкурентные тесты на SQLite доказывают сериализацию, а не пересечение; старые предложения не чистятся; клиенты опрашивают API (без WebSocket). Accept по уже отменённой поездке решает T07 часть B.
