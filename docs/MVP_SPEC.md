# Исполнимая спецификация backend MVP

Дата: 2 ноября 2026 года. Источник подтверждённых решений: [BACKEND_PLAN.md](../BACKEND_PLAN.md).

## 1. Статус решений

Пользователь выбрал Алматы/KZT, username/password, Google позже, ближайшего водителя с 30 секундами на ответ, реальные дорожные маршруты, учебный тариф, наличные и Kaspi по своей ссылке. Это требования.

Остальные конкретные значения ниже — **рабочие допущения оркестратора для автономной реализации**, а не ответы пользователя. Они обратимы и становятся базой работы при запуске промптом из `CLAUDE_START.md`. Не требуется повторный опрос перед каждой карточкой. Изменения этих допущений фиксируются в ADR и согласуются, если меняют пользовательское поведение или объём.

Роли участников команды, дата защиты и отчёт преподавателю не блокируют разработку. Фронтенд не реализуется в этом пакете.

## 2. Объём и роли

- `passenger`: профиль, маршрут/цена, создание и отмена своей поездки, статус и история, выбор способа и отметка оплаты.
- `driver`: профиль и автомобиль, доступность, координаты, предложения, выполнение принятой поездки, просмотр оплаты своей поездки.
- `admin`: допуск водителей, ограниченное чтение пользователей/поездок и их оплат.
- Регистрация позволяет выбрать только passenger или driver. Admin создаётся отдельной локальной командой, не публичной регистрацией.
- У водителя одна машина в MVP. До заполнения профиля/машины и допуска admin водитель не получает заказы.
- Смена ролей, рейтинги, промокоды, чат, push/SMS, несколько остановок, заказы ко времени и онлайн-эквайринг вне объёма T00–T10.

## 3. Общий контракт API

- Префикс `/api/v1`. JSON; UUID для внешних идентификаторов; UTC ISO 8601 для времени.
- Координаты: объект `{longitude, latitude}`, SRID 4326. Проверка диапазонов и порядка координат обязательна.
- Дистанция — целые метры, длительность — секунды, цена — целое число тенге и `currency: "KZT"`.
- Ошибка: `{"error":{"code":"...","message":"...","details":{}},"request_id":"..."}`. `details` не содержит секретов.
- 401 — неаутентифицирован, 403 — запрещённое действие роли, 404 — отсутствующий либо недоступный чужой объект, 409 — конфликт состояния/идемпотентности, 422 — некорректные поля, 503 — недоступная внешняя возможность.
- Списки: `items`, `limit`, `offset`, `total`; limit по умолчанию 20, максимум 100; стабильный порядок `created_at DESC, id DESC`.
- Изменяемые статусы не доступны через произвольный PATCH. Есть именованные команды с проверкой текущего состояния.
- OpenAPI содержит схемы, ошибки и cookie/security-схему выбранной аутентификации.

## 4. Вход и сессии

Рабочий выбор для монолита и будущего React: серверные сессии, без обязательного JWT/refresh-слоя.

- Username: 3–32 символа ASCII из букв, цифр и `_`; уникальность без учёта регистра. Пароль: 10–128 символов, поддерживаемое безопасное хеширование.
- Пароли не возвращаются и не логируются. Ошибка входа не раскрывает, существует ли username.
- Случайный криптографически стойкий session token в HttpOnly cookie; в БД только его хеш. Срок сессии — 7 дней; logout отзывает сессию.
- Cookie `SameSite=Lax`, `Secure` включён вне явно выбранной локальной HTTP-среды. Origin/CORS allowlist задаётся конфигурацией, credentials не сочетаются с wildcard origin.
- Для изменяющих запросов с сессией нужна CSRF-защита. Токен возвращается аутентифицированному клиенту через безопасный read-endpoint; logout и смена сессии не оставляют рабочие старые полномочия. Для login/register проверяется допустимый browser Origin. Решение и тесты описываются в ADR T02.
- Клиент Swagger/HTTPX должен уметь пройти вход и сделать защищённый запрос. API не требует уже существующего фронтенда.
- Ограничение перебора входа для локального одного процесса допускается простым ограниченным in-memory limiter с явным описанием ограничения; Redis не добавляется. Нужны bounded storage и тест времени, а не бесконечный словарь.
- Google — T11, отдельно после MVP. Парольный сброс, email-рассылки и SMS сейчас не требуются.

## 5. География, маршруты и тариф

- Алматы — пилотный город. В MVP клиент передаёт точки на карте; поиск адресов и геокодирование отложены.
- Не заявлять строгую муниципальную геозону без отдельного согласованного полигона. Географические диапазоны валидируются, радиус назначения действует относительно pickup.
- Выбор первого маршрутного адаптера — openrouteservice Directions для автомобиля. До фиксации версии клиент сверяет официальные условия/лимиты. Если реальная проверка Алматы покажет непригодность, оформить обоснованную замену без автоматического подключения платного тарифа.
- [Официальная документация Directions](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/).
- Нормализованный `RouteResult`: distance_m, duration_s, route_geometry, provider. Геометрия GeoJSON с порядком lon/lat.
- `ROUTING_API_KEY` приходит через окружение. Нет ключа — явный `routing_unavailable`; тестовый адаптер используется только в тестах/явно обозначенном demo-режиме.
- Ограниченные таймауты, проверка ответа, безопасные ограниченные повторы для временных ошибок. Внешний запрос не держит длинную транзакцию БД.
- Цена: `ROUND_HALF_UP(max(800, 500 + 120 * distance_m / 1000 + 20 * duration_s / 60))` KZT, вычисление через Decimal.
- Версия тарифа `edu-v1`; пример 10 000 м/1500 сек → 2200 ₸. Отрицательные/нечисловые метрики запрещены.
- Сервер сохраняет quote с маршрутом, ценой и владельцем; срок quote — 5 минут. Создание поездки использует свой непросроченный quote, не сумму из тела клиента.
- Цена фиксируется при создании поездки; симуляция движения и задержки не изменяют её.

## 6. Поездка и назначение

### Состояния поездки

```text
searching → assigned → arrived → in_progress → completed
searching → no_driver
searching / assigned / arrived → cancelled
assigned / arrived → searching  (водитель освободил назначение)
```

`completed`, `cancelled`, `no_driver` — терминальные. Предложение водителю — отдельная сущность со статусами `pending`, `accepted`, `rejected`, `expired`, `revoked`; это не состояние поездки.

### Рабочие ограничения

- У пассажира максимум одна активная поездка: searching/assigned/arrived/in_progress.
- У водителя максимум одна принятая активная поездка и максимум одно активное предложение. Ограничения защищены транзакциями и БД.
- Кандидат: допущенный водитель, online, без активной поездки/резерва, последняя координата не старше 60 секунд, расстояние до pickup не более 5 км.
- «Ближайший» в первой версии — геодезическое расстояние до pickup (haversine в метрах на SQLite, ADR 0001). Маршруты поездки при этом дорожные. При одинаковом расстоянии порядок детерминирован ID.
- Предлагаем по одному кандидату. TTL предложения 30 секунд по серверным часам; при `now >= expires_at` принятие недопустимо.
- После отказа/истечения — следующий кандидат. В рамках одного поиска уже рассмотренному водителю повторно не предлагаем.
- Общий бюджет поиска — 180 секунд. При отсутствии пригодных кандидатов на шаге либо истечении бюджета — `no_driver`. Пассажир может создать новый заказ.
- Пассажир отменяет свою поездку до in_progress без штрафа. Отмена отзывает предложение или освобождает назначенного водителя.
- Назначенный водитель отмечает arrived, затем start, затем complete. Чужой водитель не может менять поездку.
- До начала водитель может освободить назначение с причиной; поездка возвращается в searching с новым 180-секундным поиском, освободившийся водитель исключается из этого поиска.
- Во время in_progress обычная отмена отключена. Аварийное закрытие/споры не входят в MVP.
- Завершение освобождает водителя, сохраняет историю и создаёт/открывает запись неоплаченной стоимости; денежный статус отдельный.
- Если водитель перестал передавать координаты во время принятой поездки, API показывает время последнего обновления; автоматически завершать или отменять поездку по этому факту нельзя.

### Перезапуск и гонки

- Дедлайны и предложения сохраняются в БД. Периодический управляемый цикл внутри приложения может обрабатывать истечение; интервал порядка 1 секунды, значение конфигурируемое.
- После перезапуска просроченные pending предложения приводятся к актуальному состоянию. Проверка принятия всегда проверяет deadline в транзакции, даже если цикл ещё не сработал.
- Повторный проход цикла и два процесса не должны выдавать двойное назначение. Использовать условные обновления/блокировки и ограничения; никаких решений, основанных только на памяти процесса.
- API клиента пока использует polling. WebSocket/SSE не обязательны.
- Создание quote/поездки и принятие предложения имеют описанные правила повторов. Для создания поездки обязателен `Idempotency-Key`: одинаковый ключ и тело возвращают тот же результат, другой payload с тем же ключом даёт 409. Scope — пользователь и операция.
- Принятие уже принятого этим водителем предложения возвращает прежний успешный результат; после expiry/cancellation/при чужом владельце не создаёт назначение.

## 7. Оплата

Решение владельца от 3 ноября 2026 года — [ADR 0010](decisions/0010-pay-before-order.md): способ выбирается до заказа (заменяет поток ADR 0009; ссылка Kaspi — как в ADR 0009).

- Payment отдельно от Ride, одна запись на поездку: `id`, `ride_id` (unique), `amount_kzt`, `currency = KZT`, `method` (`cash`/`kaspi_link`), `status` (`unpaid`/`paid`/`refunded`), `paid_at`, `refunded_at`, `created_at`, `updated_at`. CHECK: `unpaid` — без времён, `paid` — только `paid_at`, `refunded` — оба. Журнала изменений нет.
- `POST /rides` принимает `payment_method` (`cash` по умолчанию); оплата создаётся в транзакции заказа с суммой поездки. `cash` → `unpaid`; `kaspi_link` → сразу `paid` (имитация списания; ссылку фронтенд открывает из `payment_url` сразу после заказа). `kaspi_link` без ссылки — 503 `kaspi_unavailable`, поездка не создаётся.
- Отмена пассажиром или `no_driver` при `paid` → `refunded` (`refunded_at`) в той же транзакции (имитация возврата). Release водителем оплату не меняет.
- Наличные: после `completed` назначенный водитель вызывает `POST /rides/{id}/payment/cash-received` → `paid`; повтор — 200 тот же ответ. Посторонний — 404 `ride_not_found`; пассажир и admin — 403 `payment_action_forbidden`; не завершена — 409 `ride_not_completed`; не `cash` — 409 `invalid_payment_transition`. Порядок блокировок `rides → payments`.
- `GET /rides/{id}/payment` видят пассажир, назначенный водитель и admin с момента заказа; посторонний — 404 `ride_not_found`. Ответ: `ride_id`, `amount_kzt`, `currency`, `method`, `status`, `paid_at`, `refunded_at`, `payment_url` (только при `kaspi_link`). Ответы поездки, история и admin-список содержат `payment_method` и `payment_status`.
- Ссылка приходит из `KASPI_PAYMENT_URL` (хост `pay.kaspi.kz`), не из тела запроса; параметр суммы не угадывается. Фронтенд строит QR из URL или открывает его на телефоне.
- Реальных платежей и банковских API нет; `paid` и `refunded` — учебные отметки, сервер не проверяет движение денег. Эквайринг, webhooks и автоматическая сверка вне объёма. Наличный сценарий не зависит от Kaspi.

## 8. Минимальная поверхность API

Имена ниже — контракт стартовой реализации; при необходимости уточнить до зависимой задачи и отразить в OpenAPI.

| Область | Маршруты после `/api/v1` | Владелец |
| --- | --- | --- |
| Вход | POST `/auth/register`, `/auth/login`, `/auth/logout`; GET `/auth/session` | T02 |
| Профиль | GET/PATCH `/users/me`; GET/PATCH `/drivers/me`; PUT `/drivers/me/availability`, `/drivers/me/location` | T03 |
| Допуск | GET `/admin/drivers`; POST `/admin/drivers/{id}/approve` | T03 |
| Маршрут | POST `/geo/route` | T04 |
| Quote/создание | POST `/rides/quotes`, POST `/rides`; GET `/rides/{id}` | T05 |
| Предложения | GET `/drivers/me/offers`; POST `/ride-offers/{id}/accept`, `/ride-offers/{id}/reject` | T06 |
| Поездка | POST `/rides/{id}/arrive`, `/start`, `/complete`, `/cancel`, `/release` | T07 |
| Оплата | `payment_method` в POST `/rides`; GET `/rides/{id}/payment`; POST `/rides/{id}/payment/cash-received` | T08, ADR 0010 |
| История | GET `/rides`; GET `/admin/rides`, `/admin/users` | T09 |

Health endpoints вне префикса: `/health/live`, `/health/ready`. Они не раскрывают настройки или секреты.

Каждая карточка описывает роли и проверки соответствующих команд; общее наличие маршрута не даёт право любой роли его вызывать.

## 9. Приёмка и внешние зависимости

Полный сценарий: регистрация пассажира и водителей → допуск/online/координаты → реальный маршрут и quote → поездка → отказ/timeout первого кандидата → принятие следующим → arrived/start/complete → водитель подтверждает наличные (или Kaspi, оплаченный при заказе) → история.

Тесты сценария детерминированы и используют контролируемые ответы маршрутизации. Для признания реальной внешней интеграции нужен отдельный реальный запрос в Алматы с ключом владельца.

Отсутствие ключа маршрутизации не блокирует реализацию и проверку адаптера, но оставляет настоящий сквозной показ с маршрутами `external_pending`. Без Kaspi-ссылки кнопка/возможность недоступна, без Google credentials T11 не выполняется. Эти ограничения отражаются в FINAL, а не скрываются.

Сессии, координаты и payment records не удаляются административным generic CRUD. Для MVP достаточно документированных правил очистки одноразовых тестовых данных; сроки хранения реальных пользовательских данных остаются будущим решением.
