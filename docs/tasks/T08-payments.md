- Общие правила: [CLAUDE.md](../../CLAUDE.md), [спецификация](../MVP_SPEC.md), [оркестрация](../../ORCHESTRATION.md).

## Цель

Отделить оплату от завершения поездки и выдать клиенту честный контракт cash/Kaspi-link.

## Область изменений

modules/payments/, payment tests и миграции; ограниченное согласованное изменение rides completion service. Не менять history read-router T09.

Общие файлы передаются одному владельцу; не редактировать их конкурентно. Нет права расширять задачу до фронтенда, CI или новой инфраструктуры.

## Реализация

1. Создать/открыть unpaid payment на completed ride ровно один раз; сумма берётся из server ride snapshot.
2. Разрешённые смена метода, report и confirm по MVP_SPEC; cash подтверждает назначенный driver/admin, Kaspi — admin с reference после ручной сверки.
3. Сохранить actor/time/method и verification=manual. Повтор confirm не создаёт новое начисление.
4. Payment instructions возвращают сумму/KZT и ссылку из конфигурации при наличии; QR отображает будущий клиент.
5. Нет KASPI_PAYMENT_URL — cash работает, Kaspi недоступен. Валидировать https и допустимый домен после получения ссылки.
6. Никаких выдуманных webhook/deeplink параметров, автоматического paid при redirect и реальных транзакций в тестах.

## Сначала тесты: RED → GREEN → REFACTOR

- Cash confirmation после completed, запрет чужому driver/passenger.
- Kaspi report остаётся reported; redirect/return/QR не подтверждает платёж.
- Repeated confirm, forged amount, disabled Kaspi, попытка подменить URL.
- Complete + payment creation при ошибке не оставляют противоречивое состояние; concurrent повтор не создаёт дубль.

Для каждого нового поведения сохранить команду и содержательную причину RED, затем результат GREEN. После рефакторинга повторить затронутые проверки. Баг сначала воспроизводится тестом.

## Миграции

Payment record + audit, один payment на ride. В паре T08/T09 владеет изменением схемы.

## Критерии приёмки

- [ ] Наличный полный сценарий проходит без внешних зависимостей.
- [ ] API отличает statement пассажира от ручного подтверждения; все подтверждения аудитируются.
- [ ] Kaspi-link протестирован на контролируемой безопасной конфигурации; фактическая ссылка владельца отдельно external_pending.
- [ ] Сумма неизменна и подтверждение одного платежа не затрагивает другие поездки.

## Проверки

Lint/types; payment unit/API/integration/race tests; migration tests; cash E2E; проверка реальной ссылки без оплаты только после её получения.

Указанные каталоги тестов — целевое расположение; при обоснованном уточнении записать реальные команды в отчёте. Команда, которая не запускалась, не отмечается как пройденная.

## Внешние зависимости

Пользователь пришлёт KASPI_PAYMENT_URL. Доступа к автоматической банковской сверке нет; такую возможность не заявлять.
