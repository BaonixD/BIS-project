# T06: Назначение ближайшего водителя и 30-секундные предложения

## Паспорт

- Статус при подготовке: queued; актуальный статус ведётся в [очереди](../TASKS.md).
- Зависимости: T05.
- Плановая ветка: `task/t06-dispatch`.
- База: актуальный проверенный `integration/backend-mvp` после зависимостей.
- Исполнитель: Opus 5.5 / `bis-implementer`; ревью: `bis-reviewer` либо явно обозначенная самопроверка.
- При старте заполнить: base SHA, реальная ветка/worktree, владелец, test DB/порты/Compose project.
- При передаче заполнить: result SHA, команды и [отчёт](../reports/README.md).
- Общие правила: [CLAUDE.md](../../CLAUDE.md), [спецификация](../MVP_SPEC.md), [оркестрация](../../ORCHESTRATION.md).

## Цель

Надёжно выбирать ближайшего допустимого водителя, обрабатывать отказ/таймаут и восстанавливаться после перезапуска.

## Область изменений

modules/rides/dispatch.py, offers schemas/router/repository и изменения service по созданию/назначению; database revisions; управляемый lifecycle loop через координатора.

Общие файлы передаются одному владельцу; не редактировать их конкурентно. Нет права расширять задачу до фронтенда, CI или новой инфраструктуры.

## Реализация

1. Кандидаты по geodesic distance PostGIS ≤5 км, свежесть ≤60 сек, approval/online и отсутствие busy/reservation; deterministic tie-break.
2. Последовательная offer на 30 сек; общий поиск 180 сек; skip ранее рассмотренных кандидатов, no_driver по условиям MVP_SPEC.
3. GET own offers; accept/reject с owner check, проверкой deadline/current ride status и atomic assignment.
4. Сохранить search/offer state в БД; безопасный повторный processing и единственный управляемый фоновый цикл монолита.
5. Поздний accept запрещён независимо от того, успел ли expiry loop обновить строку.
6. Согласовать порядок блокировок, constraints pending offer per ride/driver и active ride per driver. Обрабатывать конфликт ограничений как штатный исход.

## Сначала тесты: RED → GREEN → REFACTOR

- Ближайший/неподходящий/stale/out-of-radius водитель, ровно граничное время, tie-break.
- Отказ/30-секундный timeout ведёт к следующему; отсутствие кандидатов и лимит поиска.
- Одновременные accept/reject/expiry, два заказа на одного водителя и два process pass.
- Перезапуск с просроченными pending восстанавливает состояние без двойного назначения.

Для каждого нового поведения сохранить команду и содержательную причину RED, затем результат GREEN. После рефакторинга повторить затронутые проверки. Баг сначала воспроизводится тестом.

## Миграции

Ride offers/search attempts и ограничения одной pending offer. Нельзя использовать текущее время в предикате partial unique index.

## Критерии приёмки

- [ ] Полный поиск/ответ проходит через API и сохраняется в БД.
- [ ] Нет двойного назначения/резерва; проигравший конкурентный запрос получает определённый результат.
- [ ] Тесты управляют часами и не ждут 30 реальных секунд каждый раз.
- [ ] Shutdown завершает loop; без Kafka/Celery/Redis и без пропажи бизнес-состояния при restart.

## Проверки

Lint/types; unit dispatch с контролируемым временем; API offers; PostgreSQL concurrency and restart-state tests; migration upgrade/check.

Указанные каталоги тестов — целевое расположение; при обоснованном уточнении записать реальные команды в отчёте. Команда, которая не запускалась, не отмечается как пройденная.
