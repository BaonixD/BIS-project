# T01: SQLite, Alembic и тестовая изоляция

## Паспорт

- Статус при подготовке: queued; актуальный статус ведётся в [очереди](../TASKS.md).
- Зависимости: T00.
- Плановая ветка: `task/t01-database`.
- База: актуальный проверенный `integration/backend-mvp` после зависимостей.
- Исполнитель: Opus 5.5 / `bis-implementer`; ревью: `bis-reviewer` либо явно обозначенная самопроверка.
- При старте заполнить: base SHA, реальная ветка/worktree, владелец, test DB-файл/порты.
- При передаче заполнить: result SHA, команды и [отчёт](../reports/README.md).
- Общие правила: [CLAUDE.md](../../CLAUDE.md), [спецификация](../MVP_SPEC.md), [оркестрация](../../ORCHESTRATION.md).

## Цель

Подготовить файловую SQLite-БД (ADR 0001), предсказуемое управление сессиями и миграциями и безопасную тестовую БД.

## Область изменений

database/, alembic/, alembic.ini, tests/conftest.py, tests/integration/db/, tests/migrations/, readiness, связанные настройки и README.

Общие файлы передаются одному владельцу; не редактировать их конкурентно. Нет права расширять задачу до фронтенда, CI или новой инфраструктуры.

## Реализация

1. Настроить async engine/session factory, naming conventions, Base и явный импорт metadata без запуска приложения.
2. Настроить SQLite: foreign_keys=ON, WAL, busy_timeout, транзакции через BEGIN IMMEDIATE, UTC-aware тип времени. Alembic с render_as_batch.
3. Описать и реализовать команды upgrade/check и создание отдельной одноразовой тестовой БД-файла. Не использовать `:memory:` для интеграционных проверок.
4. Фикстуры надёжно изолируют данные, включая тесты с независимыми соединениями и реальными commit для гонок; один rollback fixture не должен маскировать concurrency.
5. Проверить test DATABASE_URL перед разрушительной очисткой. Рабочая/demo БД не подходит.
6. Readiness проверяет соединение и нужную готовность схемы; закрытие engine происходит через lifespan.

## Сначала тесты: RED → GREEN → REFACTOR

- Сначала интеграционные проверки реальной сессии, foreign keys, UTC-времени, сериализации записи и изоляции данных.
- Неподнятая БД — ошибка окружения, а не RED. После установки окружения проверить поведение на незавершённой реализации.
- Миграционная проверка сначала задаёт ожидаемую процедуру пустая БД → head → отсутствие diff; дальнейшие задачи расширяют её своими таблицами.

Для каждого нового поведения сохранить команду и содержательную причину RED, затем результат GREEN. После рефакторинга повторить затронутые проверки. Баг сначала воспроизводится тестом.

## Миграции

Владелец первичной настройки Alembic. Начальную прикладную ревизию создавать только для реальных объектов; предметные таблицы вводятся последующими задачами.

## Критерии приёмки

- [ ] На пустой отдельной БД воспроизводима процедура подготовки и upgrade; работают foreign keys и UTC-время.
- [ ] alembic check не показывает ложных операций.
- [ ] Две тестовые среды не изменяют данные друг друга; закрываются сессии/пулы.
- [ ] Ни main.py, ни импорт моделей не создают схему и не запускают seed.

## Проверки

Линтинг/типы; uv run pytest tests/integration/db tests/migrations; upgrade head и alembic check на одноразовой БД; повторный upgrade.

Указанные каталоги тестов — целевое расположение; при обоснованном уточнении записать реальные команды в отчёте. Команда, которая не запускалась, не отмечается как пройденная.

## Внешние зависимости

Нет. Реальные проверки на файловой SQLite-БД обязательны перед статусом integrated.

## Передача

Передать точный SHA, список изменений, RED/GREEN, результаты проверок, миграции, ограничения и следующий шаг. Главная сессия выполняет ревью, интеграцию и обновляет `docs/TASKS.md`; исполнитель не объявляет сам себе приёмку.
