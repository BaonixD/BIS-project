- Статус при подготовке: deferred; актуальный статус ведётся в [очереди](../TASKS.md).
- Зависимости: T10 и отдельная команда пользователя.
- Плановая ветка: `task/t11-google`.
- База: актуальный проверенный `integration/backend-mvp` после зависимостей.
- Исполнитель: Opus 5.5 / `bis-implementer`; ревью: `bis-reviewer` либо явно обозначенная самопроверка.
- При старте заполнить: base SHA, реальная ветка/worktree, владелец, test DB/порты/Compose project.
- При передаче заполнить: result SHA, команды и [отчёт](../reports/README.md).
- Общие правила: [CLAUDE.md](../../CLAUDE.md), [спецификация](../MVP_SPEC.md), [оркестрация](../../ORCHESTRATION.md).

## Цель

После завершения основного MVP добавить настоящий Google-вход без нарушения локальных аккаунтов и контроля сессий.

## Область изменений

modules/auth/ Google adapter и callbacks, external identity model, соответствующие security tests и документация.

Общие файлы передаются одному владельцу; не редактировать их конкурентно. Нет права расширять задачу до фронтенда, CI или новой инфраструктуры.

## Реализация

1. Перед реализацией сверить актуальный Google OIDC flow и поддерживаемую библиотеку; не писать собственный JWT verifier.
2. Client ID/secret/redirect URI через окружение; registered callback, state/nonce и защита от повторов согласно выбранному flow.
3. Provider identity привязана по проверенному issuer+subject. Связывание с существующим локальным аккаунтом требует доказанного владения аккаунтом.
4. Использовать существующие session/cookie/CSRF правила. Не допускать automatic privilege escalation по email.
5. Записать ограничения localhost callback и внешней настройки; не создавать Google project/платные сервисы автоматически.

## Сначала тесты: RED → GREEN → REFACTOR

- Неверная подпись/audience/issuer/expiry, неправильный state/nonce и повтор callback.
- Попытка захвата аккаунта через email, повтор входа тем же subject, конфликт привязки.
- Google пользователь не получает admin/approved driver автоматически.

Для каждого нового поведения сохранить команду и содержательную причину RED, затем результат GREEN. После рефакторинга повторить затронутые проверки. Баг сначала воспроизводится тестом.

## Миграции

External identity с уникальностью provider+subject; миграция не связывает пользователей автоматически по совпадающему непроверенному email.

## Критерии приёмки

- [ ] Детерминированные security/adapter tests проходят.
- [ ] Реальный Google login проверен с credentials либо external_pending, это явно указано.
- [ ] Username/password продолжает работать; миграция не портит существующие аккаунты.
- [ ] Задача выполняется только отдельным запуском, не расширяет T00–T10 без команды.

## Проверки

Lint/types; auth security/API/integration tests; migration tests; реальный localhost login при предоставленных credentials.

Указанные каталоги тестов — целевое расположение; при обоснованном уточнении записать реальные команды в отчёте. Команда, которая не запускалась, не отмечается как пройденная.

## Внешние зависимости

Google client credentials и настройка callback. До отдельной команды статус deferred.
