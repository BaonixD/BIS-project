# План Astra: время прибытия, документы водителя, достижения и поддержка

Дата: 16 ноября 2026 года. Подготовил GPT-6 Astra.
Исполнитель следующего этапа: GPT-6.1 Sol, после переключения модели пользователем.
Статус: **план готов к реализации; код функций в этом проходе не изменяется**.
База анализа: `main`, `8a7b371`; Alembic head: `a3267d91e0b4`.
Перед реализацией сверить текущие Git HEAD, миграции и изменения пользователя.

## 1. Результат для пользователя

1. Пассажир видит отдельно: сколько ждать водителя, сколько ехать, расстояние
   и примерное время прибытия. Значения обновляются по текущей позиции водителя.
2. Водитель загружает удостоверение личности и водительские права в PDF,
   отправляет пакет на проверку и видит решение администратора.
3. Администратор открывает документы в карточке заявки, возвращает пакет с
   причиной или одобряет водителя и назначает максимальный класс автомобиля.
4. Пассажиры и водители видят небольшой прогресс и достижения в профиле.
5. При проблеме можно открыть обращение, описать ситуацию и получить ответ
   администратора прямо в приложении, при необходимости привязав поездку.
6. Все новые тексты доступны на RU / Қазақша / English простыми фразами.

## 2. Рабочие решения для реализации

Это выбранные для плана значения, а не утверждение, что пользователь отдельно
согласовал каждое ограничение. Sol может выполнять их без повторного опроса,
пока пользователь не уточнил иначе.

- Сохраняем FastAPI + async SQLAlchemy + SQLite, модульный монолит и текущий polling.
- Документы: два отдельных слота `identity_card` и `driver_license`.
  Каждый PDF может содержать обе стороны документа. По одному актуальному файлу
  на слот, максимум 10 MiB и 10 страниц на файл; без пароля.
- Проверка вручную администратором. OCR, распознавание ИИН, проверка по госбазам,
  автоматическое подтверждение личности и юридическая сертификация не входят в этап.
- Файлы хранятся приватно на сервере, метаданные — в SQLite. Публичных URL нет.
- Поддержка: тикеты с перепиской внутри сайта, отвечают администраторы. Текст,
  категория проблемы, необязательная поездка. Вложения, email, Telegram и бот
  не нужны для первой версии.
- Геймификация: только значки и прогресс; без денежных бонусов, изменения цены,
  конкуренции по скорости, штрафов и изменения приоритета назначения заказов.
- Прогнозы OSRM приблизительные, без учёта пробок. Их нельзя выдавать за точное
  время или использовать для автоматического завершения поездки.

## 4. Прогноз прибытия, расстояние и длительность

### 4.1. Поведение интерфейса

| Состояние | Что показать |
| --- | --- |
| Выбор тарифа | «8,4 км · около 18 мин в пути»; это путь пассажира от A до B |
| Поиск водителя | Расстояние и длительность поездки; время подачи пока неизвестно |
| Водитель назначен | «Приедет примерно через 5 мин», «До вас 1,8 км», «Около 14:35» |
| Водитель на месте | «Водитель на месте», таймер ожидания; ETA подачи больше не показывать |
| Поездка началась | «До прибытия около 12 мин», «Осталось 5,2 км», «Прибытие около 14:52» |
| Завершена | Исходное расчётное расстояние и фактическая длительность `completed_at - started_at` |
| Отмена / нет водителя | Прекратить обновления прогноза, убрать активный таймер |

Перед назначением нет данных для честного прогноза подачи — не подставлять время
самой поездки. До начала движения отдельно показывать «В пути ~18 мин» без
обещания точного времени прибытия в конечную точку. Карточка не прыгает при polling:
фиксированные позиции трёх показателей, skeleton только при первой загрузке.

### 4.2. Backend-контракт

Новый `GET /api/v1/rides/{ride_id}/estimate` с теми же правами видимости поездки,
что у `GET /rides/{ride_id}`. Admin может читать, посторонний получает 404.
Отдельный запрос изолирует медленный OSRM от критичного обновления статуса поездки.

Ответ `RideEstimateResponse`:

- `ride_id`, `ride_status`, `driver_id`, `generated_at` (UTC).
- `trip_distance_m`, `trip_duration_s` — исходный снимок маршрута заказа.
- `target: pickup | dropoff | null`.
- `distance_m`, `duration_s`, `arrival_at` — nullable, только для текущей цели.
- `source: road | approximate | unavailable`, `stale: bool`.
- `location_updated_at: datetime | null`.

Сценарий сервиса `rides/estimates.py`:

1. Короткая read-транзакция: проверить права, прочитать статус, текущего водителя,
   координаты и timestamp. Закрыть транзакцию.
2. Для `assigned` цель — pickup; для `in_progress` — dropoff.
   Для остальных состояний вернуть `target=null` и исходную сводку без OSRM.
3. Свежесть координат: не старше 60 с по внедрённому `Clock`.
   Нет координат / устарели — `unavailable`, без фиктивного движущегося таймера.
4. Вызвать существующий `RoutingProvider.get_route()` **вне DB-транзакции**.
   При совпадающих точках вернуть 0 м / 0 с без ошибки маршрута; подпись «Рядом»,
   но состояние `arrived` может изменить только водитель.
5. Если провайдер недоступен, для свежих координат допустим явно приблизительный
   fallback: haversine × 1,3 и 25 км/ч; `source=approximate`.
   При подтверждённом `route_not_found` вернуть unavailable, не проводить путь
   по прямой через непроходимую географию.
6. Коротко перечитать статус, назначение и timestamp после внешнего запроса.
   При смене водителя/этапа отбросить старый результат. При изменении позиции
   не выдавать старую оценку как рассчитанную по новой; вернуть прежний timestamp
   и корректную свежесть. Не создавать бесконечный цикл повторов.

Кэш внутри процесса: TTL 15 с, лимит 500 записей; ключ включает ride_id,
назначенного driver_id, этап/цель и `location_updated_at`. Объединять конкурентные
одинаковые запросы одним in-flight вызовом. Ошибки не кэшировать надолго.
Создавать/закрывать кэш в lifespan; не использовать глобальное состояние между
тестовыми приложениями. Доступ к кэшу — только после проверки прав.
`arrival_at = generated_at + duration_s`, а не каждый render «сейчас + старая длительность».

Фронт: `useRideEstimate()` с интервалом 15 с только для активной цели и видимой
вкладки. При `stale`, ошибке или старых данных — «Обновляем время» / «Время недоступно»,
последнее значение можно показать приглушённо с подписью «Обновлено … назад».
По истечении ETA без подтверждённого прибытия — «Время уточняется», не отрицательное
число и не вечная «1 минута». Обычный polling статуса остаётся 3 с.

Не уменьшать километры по таймеру: расстояние меняется только по новому расчёту.
Не называть исходное расстояние фактически пройденным: трек движения не хранится.

### 4.3. Проверки

- Разные цели для подачи и поездки; совпадающие точки; нет/устарели координаты.
- OSRM timeout, недоступность, отсутствие маршрута и помеченный fallback.
- Кэш, concurrent single-flight, TTL, смена водителя, смена этапа во время HTTP.
- Не раскрывать координаты чужой поездки; отмена прекращает запросы.
- Frontend различает время подачи и длительность поездки; локализованные минуты,
  километры, время Алматы; истёкший прогноз не обещает «уже прибыл».

## 5. Документы и проверка водителя

### 5.1. Сценарий водителя

`/driver/documents` открывается из профиля и баннера ожидания допуска.
Две аккуратные карточки: «Удостоверение личности» и «Водительские права».
В каждой: иконка PDF, имя, размер, время загрузки, статус, действия
«Загрузить / Заменить / Посмотреть». Подпись: «PDF, до 10 МБ; обе стороны в одном файле».
Видимый прогресс запроса/загрузка, ошибка рядом со своим слотом, повтор после сбоя.
При перезагрузке страницы состояние берётся с API.

Общий checklist: профиль заполнен, машина добавлена, удостоверение загружено,
права загружены. «Отправить на проверку» активна только для полного пакета.
После отправки — «На проверке». После возврата — причина и «Исправить документы».
После одобрения — «Документы проверены». Простой текст EN/KK/RU.

### 5.2. Модель данных и состояния

Новый модуль `modules/documents/`, функциональные service/router/storage/validation.

`driver_document_packages`:
- `id`, `driver_id`, `version` (монотонная на водителя),
  `status: draft | pending | approved | rejected | superseded`;
- `profile_revision` — версия существенных данных водителя на момент отправки;
- `created_at`, `submitted_at`, `reviewed_at`, `reviewed_by`, `review_note`;
- UNIQUE(driver_id, version), один текущий пакет (partial unique index для
  состояний кроме superseded), CHECK связи review-статуса и времени решения.

`driver_documents`:
- `id`, `package_id`, `kind: identity_card | driver_license`, `storage_key`,
  `original_filename`, `size_bytes`, `sha256`, `page_count`, `created_at`;
- UNIQUE(package_id, kind), положительный размер, 1–10 страниц, FK.

`driver_profiles`: добавить `profile_revision` и `document_requirement_exempt`
(описание миграции ниже). Значимые изменения ФИО/прав/машины повышают revision.
Номер телефона сам по себе не требует повторного рассмотрения.

Существующие `approval_status=pending/approved` оставить для разрешения работы.
Отдельный пакет содержит более подробный статус документов:

- первый upload создаёт draft; upload другого слота дополняет тот же draft;
- submit: draft → pending, оба файла + профиль + машина обязательны;
- pending неизменяем: замена возможна только через явное «Исправить документы»;
- revise делает прежний пакет superseded, создаёт новый draft с копиями ссылок
  на текущие файлы, увеличивает версию, отзывает допуск и снимает с линии;
- approve/reject адресованы конкретному package_id/version и profile_revision;
- approve: pending → approved и driver → approved в одной транзакции;
- reject: pending → rejected, причина 3–500 символов, водитель остаётся pending;
- повтор того же решения возвращает прежний результат; противоположное решение
  по уже рассмотренному пакету — 409; просмотр устаревшей версии не позволяет одобрить новую.

При изменении значимых данных автоматически supersede текущую поданную/одобренную
версию и создать draft на новую profile_revision. Прежние файлы могут быть
предзаполнены, но водитель должен проверить и отправить новую версию явно.

Замену/удаление документов и отзыв пакета запретить во время принятой активной
поездки (409), как сейчас запрещено изменение машины. Для свободного водителя
ревизия атомарно снимает online и отзывает pending offers. Уже принятую поездку
не обрывать. При подтверждении после загрузки повторно проверять состояние БД.

### 5.3. API

| Метод и путь (`/api/v1`) | Назначение |
| --- | --- |
| GET `/drivers/me/documents` | Текущий пакет, оба слота, checklist и возможные действия |
| PUT `/drivers/me/documents/{kind}` | multipart `file`, только draft; ответ с метаданными |
| DELETE `/drivers/me/documents/{kind}` | Удалить слот draft |
| POST `/drivers/me/documents/submit` | `{package_id, version}` → pending |
| POST `/drivers/me/documents/revise` | `{package_id, version}` → новый draft |
| GET `/documents/{document_id}/content` | Файл владельцу или admin после проверки прав |
| GET `/admin/drivers/{driver_id}/documents` | Текущий пакет и метаданные прежних версий |
| POST `/admin/drivers/{driver_id}/approve` | Расширить существующий маршрут: `{car_class?, package_id, version}` |
| POST `/admin/drivers/{driver_id}/documents/reject` | `{package_id, version, reason}` |

В существующем approve обязательность пакета проверять на сервере для всех
водителей без legacy-исключения. Нельзя обойти через старый вызов без тела.
Проверку класса машины через отдельный PATCH сохранить; она не одобряет документы.
`missing_fields` и отдельный `documents_summary` должны отличать незаполненный
профиль от неотправленного пакета, без N+1 запросов в admin-списке.

### 5.4. Хранение и просмотр PDF

- `DOCUMENT_STORAGE_DIR=./private_uploads/driver-documents`, вне frontend/public,
  исключить файлы из Git; тесты используют собственный tmp_path.
- Имена на диске генерировать сервером (UUID), пользовательское имя — только
  метаданные. Не принимать пути от клиента. Каталог и файлы доступны процессу приложения.
- Добавить multipart-зависимость и PDF-парсер в `pyproject.toml`/`uv.lock`.
  Перед выбором версии проверить совместимость с Python 3.12.
- Читать upload порциями с реальным ограничением размера; `Content-Length` не
  считать достаточной проверкой. Ограничить тело multipart до разбора, чтобы
  oversized файл не занимал диск без контроля; корректно вернуть 413.
- Проверить расширение, MIME и фактическую структуру PDF, возможность открыть,
  отсутствие шифрования, лимит страниц; не принимать HTML под видом PDF.
- Парсинг не блокирует event loop, имеет ограничение ресурсов/времени;
  запрещённые активные действия/вложения PDF отклоняются. Это базовая валидация,
  не обещание полноценного антивирусного анализа.
- Загрузка: временный файл → проверка → случайный final key → короткая DB-транзакция
  с повторной проверкой draft/version → метаданные. При rollback удалить новый файл.
  Аварийные orphan-файлы чистит отдельная команда с dry-run по списку ключей БД;
  при общем storage_key разных версий не удалять используемый файл.
- Скачивание/просмотр: cookie-auth, `Cache-Control: private, no-store`,
  `X-Content-Type-Options: nosniff`, корректный безопасный Content-Disposition.
  Логи не содержат PDF, оригинальные имена, ИИН или номера документов.
- Для встроенного просмотра предпочтителен локально установленный PDF.js:
  authenticated fetch → ArrayBuffer → canvas, без выполнения действий/ссылок PDF,
  lazy-loading worker, загрузка только открытого документа, освобождение ресурсов.
  На телефоне доступны страницы, масштаб и «Открыть/Скачать PDF».
  Если встроенный просмотр не поддерживается — рабочая кнопка скачивания.
- В выдачу пассажира никакие документы и метаданные удостоверения не включать.

### 5.5. UX администратора

В карточке водителя: информация и машина сверху, затем «Пакет документов»,
номер версии, дата отправки, две PDF-карточки и общий статус.
На десктопе просмотр документа рядом с данными; на телефоне полноэкранный диалог
с доступным закрытием, фокусом и кнопками страниц. Кнопки «Одобрить» и «Вернуть
на исправление» в аккуратной нижней панели. Причина возврата обязательна.

Список водителей: фильтры «Готовы к проверке / Нужны документы / Одобрены /
На исправлении»; badge количества новых пакетов. После решения invalidate
список, карточку и overview; показывать конфликт версии и обновлять карточку.
Одобрение выполняется только после просмотра актуального пакета, backend
проверяет пакет и заполненность независимо от состояния кнопок.

### 5.6. Миграция существующих водителей

Не выдавать старым аккаунтам фиктивное «Документы проверены».
Сохранить текущий доступ уже одобренным водителям через явный
`document_requirement_exempt=true` только для существующих approved на миграции.
В админке писать «Ранее одобрен, документы ещё не предоставлены».
Новые и ранее pending водители всегда проходят новый процесс.
При первой отправке/ревизии документов или значимом изменении профиля
legacy-исключение снимается. Добавить `POST /admin/drivers/{driver_id}/documents/request`
с обязательной причиной (3–500 символов) — действие «Запросить документы»
с теми же ограничениями активной поездки; оно снимает exemption и допуск.
Это миграционное исключение не является доказательством проверки документов.
Демо-seed нового окружения создаёт тестовые PDF без личных данных и проводит их
через нормальный сервис подачи/одобрения. Не добавлять универсальный bypass проверки.

### 5.7. Приёмка документов

Пустой/большой/повреждённый/запароленный/не-PDF файл; обе стороны в одном PDF;
ошибка диска/rollback; путь с `../`; повтор upload; новый файл после отказа;
права владельца/admin/постороннего, CSRF, прямое скачивание; загрузка двух вкладок;
approve против replace/revise; повтор решения; активная поездка; миграция legacy;
очистка без удаления файлов действующих/исторических пакетов; восстановление
бэкапа должно включать и SQLite, и приватный каталог.

## 6. Небольшая геймификация

В первом этапе достаточно трёх достижений на роль и карточки прогресса:

| Пассажир | Условие |
| --- | --- |
| Первая поездка | 1 завершённая поездка |
| Частый пассажир | 5 завершённых поездок |
| Обратная связь | Оставлены оценки после 3 разных завершённых поездок |
| Водитель | Условие |
| Первый заказ | 1 завершённая поездка водителем |
| Опытный водитель | 10 завершённых поездок |
| Высокая оценка | Средняя полученная оценка ≥ 4,8 при минимум 5 оценках |

Реализация `modules/achievements/`: read-only агрегации существующих rides/ratings,
без отдельного ledger, начисления очков и изменений `lifecycle.on_ride_completed`.
Старые поездки автоматически учитываются. Результат детерминирован, повторный
complete не создаёт повторных наград. Значок рейтинга динамический: при падении
среднего условие больше не выполнено, UI не обещает пожизненную награду.

`GET /users/me/achievements` → `{completed_rides, achievements:[{code, current,
 target, unlocked}]}`. Средний рейтинг считать по исходной сумме/числу оценок,
не по округлённой строке. Код/прогресс с сервера, локализованное название/описание
с фронтенда. Только собственные данные; роли admin возвращать пустой набор.

Профиль: небольшой блок «Достижения», 3 значка, понятный прогресс «3 из 5».
После завершения поездки/оценки обновлять запрос достижений. Без непрерывной
анимации и без навязчивых pop-up. Состояния загрузки/ошибки не мешают профилю.
Проверить пороги, отсутствие поездок, отмены, роли, старые поездки, повтор complete,
рейтинг 4,79 vs 4,80, минимальное число оценок и переводы.

## 7. Поддержка внутри приложения

### 7.1. Сценарии

- В профилях пассажира и водителя — «Поддержка».
- В активной поездке и её истории — «Проблема с поездкой», форма уже знает ride_id.
- Категории: поездка, оплата, документы, аккаунт, другое. Тема ≤120 символов,
  первое сообщение 1–2000 символов, пробельные сообщения запрещены.
- `/support`: список своих обращений, статус, дата, последнее сообщение,
  непрочитанные. `/support/{id}`: переписка и поле ответа.
- `/admin/support`: очередь обращений с поиском, статусом и категорией;
  `/admin/support/{id}`: переписка, автор, роль, ссылка на связанную поездку.
- Сообщения обычным текстом, без HTML. Администратор отвечает и закрывает вопрос.
- Показывать «Ответ появится здесь»; не обещать круглосуточную поддержку/время ответа.

### 7.2. Данные и переходы

`support_tickets`: id, owner_id, ride_id nullable, category, subject,
status `open | in_progress | resolved`, created_at, updated_at,
resolved_at, resolved_by, last_message_seq.

`support_messages`: id, ticket_id, seq, author_id, body, created_at,
client_message_id UUID; UNIQUE(ticket_id, seq), UNIQUE(author_id, client_message_id).
Первое сообщение создаётся в той же транзакции, что и тикет.

`support_reads`: ticket_id, user_id, last_read_seq; составной PK.
При отправке seq растёт под блокировкой тикета; обновляется `updated_at`.
Чтение отмечается явным POST с реально показанным seq, сервер делает monotonic max
и не принимает номер выше последнего. Это исключает потерю нового сообщения
из-за гонки загрузки и read-отметки. Непрочитанные считают чужие сообщения после seq.

- Создание → open.
- Первый ответ администратора: open → in_progress.
- Admin может закрыть open/in_progress → resolved и переоткрыть → in_progress.
- Новое сообщение владельца в resolved автоматически переоткрывает → open;
  время/автор закрытия очищаются, старые сообщения сохраняются.
- Новое сообщение admin в resolved: переоткрыть → in_progress.
- Повтор запроса с тем же client_message_id и тем же содержимым возвращает
  прежний результат; другое содержимое — 409, без дублирования сообщений.

Пользователь видит только свои тикеты; admin — все. При создании привязанной
поездки проверить, что пользователь её пассажир или назначенный водитель.
Зафиксированная привязка тикета сохраняется после release, но доступ к самой
поездке проверяется отдельно. Нельзя получить новые данные чужой поездки через тикет.
Заблокированный аккаунт пока не получает отдельный публичный канал: текущая auth
его не пропускает; не обещать поддержку из такого аккаунта. Возможность обращения
без входа — отдельное расширение, чтобы не ослаблять блокировку.

### 7.3. API и обновления

| Метод и путь (`/api/v1`) | Назначение |
| --- | --- |
| POST `/support/tickets` | `{client_request_id, category, subject, body, ride_id?}`; защита от дубля создания |
| GET `/support/tickets` | Свои обращения, status, limit, offset |
| GET `/support/tickets/{id}` | Метаданные обращения |
| GET `/support/tickets/{id}/messages` | Сообщения по `after_seq`, limit ≤50, стабильный порядок |
| POST `/support/tickets/{id}/messages` | `{client_message_id, body}` |
| POST `/support/tickets/{id}/read` | `{last_read_seq}` |
| GET `/admin/support/tickets` | Все обращения, q/status/category, пагинация |
| PATCH `/admin/support/tickets/{id}` | Смена статуса с проверкой перехода |

Для admin чтение и отправка сообщений используют общие detail/messages/read
маршруты с проверкой роли; не дублировать код отправки. `client_request_id`
для создания тикета имеет отдельный UNIQUE(owner_id, client_request_id) и fingerprint.
Ограничить частоту отправки и создания на пользователя; 429 с retry_after,
использовать Clock и существующий подход лимитов без Redis.

Polling переписки каждые 5 с только в видимой вкладке; списки/счётчики каждые 20 с.
После отправки сразу invalidate/добавить подтверждённое сообщение. Кнопку блокировать
на pending, текст сохранять при ошибке. Не скроллить вниз, если читают старые
сообщения; показать «Новые сообщения». Автоскролл только у нижнего края.
Читаемые области и ввод доступны с клавиатуры, textarea не уезжает под mobile keyboard.

Проверки: права/CSRF, привязка чужой поездки, повтор отправки и создания,
сохранение после рестарта, пагинация и отсутствие потери сообщений, seq/read гонки,
статусы/переоткрытие, пустые/длинные/XSS строки, лимиты, mobile layout, три языка.

## 8. Общие правила реализации

- Новые доменные модули: documents, achievements, support; estimates внутри rides.
  `router → service`, явные транзакции, Pydantic отдельно от ORM, единый ErrorResponse.
- Порядок блокировок согласовать с текущими `rides → offers → payments` и профилями
  водителя. Не держать SQL-транзакцию во время PDF I/O, OSRM или загрузки клиента.
- Каждая стадия со схемой получает отдельную Alembic-ревизию от фактического head.
  Ни номера будущих миграций, ни SHA не придумывать заранее.
- Настройки файлов/кэша/лимитов в config/.env.example с безопасными default.
- Использовать существующие Button, Input, StatusPill, Dialog, карточки, цвета
  и отступы. Десктопные таблицы адаптировать карточками на мобильном.
- Сохранить русский по умолчанию, RU/KK/EN, `dateFormatter`, KZT и Asia/Almaty.
  Ввод пользователя не переводить; API хранит коды статусов, не локализованные названия.
- После контрактных изменений обновить `frontend/openapi.json`, `schema.d.ts`,
  типы/hooks и fixtures; не заменять типизацию на `any`.
- Для списка admin и support проверить число SQL-запросов на 10/30 объектов.
- Не менять `.env`, реальные документы/аккаунты для тестов; использовать временные БД
  и синтетические PDF. При применении к локальному запуску сначала backup.

## 10. Итоговые проверки и демонстрация

Команды:

```bash
uv run python scripts/lint.py
uv run mypy backend/taxi_service
uv run pytest
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend test
npm --prefix frontend run build
```

Отдельно запустить доступные Playwright-сценарии на изолированной БД, а также
визуально проверить 390px и 1440px. Не считать mocks проверкой настоящего OSRM.
Реальный smoke OSRM — отдельный локальный запрос.

Сценарий демонстрации:

1. Новый водитель создаёт профиль и машину; без пакета выход на линию недоступен.
2. Загружает два синтетических PDF и отправляет на проверку.
3. Admin открывает каждый документ и возвращает пакет с причиной.
4. Водитель заменяет один файл и отправляет новую версию.
5. Admin одобряет актуальную версию и ставит Business; водитель выбирает тарифы.
6. Пассажир видит расстояние/время до заказа, после назначения — ETA подачи,
   после старта — оставшийся путь и время прибытия.
7. Стороны завершают поездку, подтверждают наличные/используют учебный Kaspi;
   в профилях виден прогресс достижений.
8. Пассажир создаёт обращение по поездке; admin отвечает, решает; ответ пользователя
   переоткрывает обращение. Проверить непрочитанные и перезагрузку страницы.
9. Пройти основные новые экраны на казахском и английском без сложных формулировок.

Готово, когда все четыре функции доступны и на backend, и на frontend,
существующий заказ/оплата/блокировки/выбор тарифов продолжают работать,
а документы доступны только их владельцу и администраторам.
