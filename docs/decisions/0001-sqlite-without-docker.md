# ADR 0001: SQLite и запуск без Docker на текущем этапе

Дата: 3 ноября 2026 года. Статус: принято владельцем проекта.

## Контекст

План Astra предполагал PostgreSQL/PostGIS в Docker Compose. Владелец проекта решил пока не запускать тяжёлые контейнеры на ноутбуке и работать на SQLite.

## Решение

- Основная и тестовая БД текущего этапа — файловая SQLite через SQLAlchemy 2 async и `aiosqlite`.
- Dockerfile и `compose.yaml` не создаются. Запуск, миграции, seed и тесты выполняются через `uv`.
- Миграции Alembic используют `render_as_batch=True`. Типы и ограничения выбираются переносимыми: `Uuid`, целые KZT, UTC-время через общий тип, `CHECK`, уникальные и partial unique индексы с `sqlite_where` и `postgresql_where`.
- Координаты хранятся как `longitude`/`latitude` (WGS 84, SRID 4326 по смыслу). Ближайший водитель определяется геодезическим расстоянием (haversine, метры) после bounding-box предфильтра в SQL; при равенстве порядок по ID.
- SQLite включается с `foreign_keys=ON`, WAL и `busy_timeout`. Пишущие транзакции начинаются через `BEGIN IMMEDIATE`, чтобы конкурентные изменения сериализовались, а не терялись. Защита от гонок по-прежнему строится на условных `UPDATE` и ограничениях БД, а не на проверках в памяти процесса.
- Тесты используют отдельный файл БД во временном каталоге, а не `:memory:`, чтобы конкурентные тесты работали через независимые соединения.

## Последствия

- Нет PostGIS, пространственного индекса и `SELECT ... FOR UPDATE`; SQLite блокирует запись на уровне всей БД. Для учебного локального MVP это приемлемо.
- Конкурентные тесты проверяют инварианты при сериализованной записи SQLite. Поведение на PostgreSQL потребует повторной проверки при переходе.
- Переход на PostgreSQL/PostGIS — отдельная последующая задача: драйвер asyncpg, ревизия для geography/spatial index и повторный прогон тестов на реальном сервере.
- Docker Compose может быть добавлен позже отдельной задачей по команде владельца.
