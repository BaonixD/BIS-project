# ADR 0011: Вход пассажиров через Google (ID token)

Дата: 3 ноября 2026 года. Статус: принято владельцем (облегчённый вариант T11). Дополняет [ADR 0003](0003-auth-sessions-csrf.md): сессии, cookie, CSRF и проверка Origin не меняются.

## Контекст

Владелец хочет кнопку «Войти через Google» для пассажиров будущего React-клиента. Client ID будет выдан позже; без него функция выключена. Карточка [T11](../tasks/T11-google.md) описывала полный OAuth-redirect с callback, state/nonce и отдельной таблицей внешних идентичностей; владелец выбрал более простой поток.

## Решение

- **Поток — Google Identity Services.** Фронтенд показывает кнопку GIS с `client_id` из `GET /api/v1/auth/providers` и получает `credential` — Google ID token (JWT). Бэкенд принимает его в `POST /api/v1/auth/google` и выдаёт обычную серверную сессию: тот же `SessionResponse`, HttpOnly cookie `taxi_session`, `csrf_token`. Redirect/callback, client secret и обмен кода не нужны.
- **Проверка — только библиотекой `google-auth`**: `google.oauth2.id_token.verify_oauth2_token(credential, request, audience=GOOGLE_CLIENT_ID)` — подпись по сертификатам Google, `iss` (`accounts.google.com`), `aud`, срок (допуск часов 10 с). Собственного JWT-верификатора нет. Дополнительно сервис требует `email_verified = true` и непустой `email`. Любой отказ — `401 invalid_google_token`; недоступность сертификатов Google (сеть, не-200) — `503 google_login_unavailable`.
- **Вне транзакции и event loop.** Проверка делает HTTP-запрос за сертификатами (таймаут 5 с вместо 120 с по умолчанию в google-auth) и выполняется через `asyncio.to_thread` до любой транзакции БД.
- **Внедрение.** Верификатор — протокол `GoogleTokenVerifier`; `create_app(google_verifier=...)` подменяет его в тестах (как `routing_provider`). Рабочий `GoogleIdTokenVerifier` всегда проверяет по-настоящему, фиктивного успеха нет. Его же проверки (подпись, issuer, audience, срок, мусор, сбой сети) тестируются офлайн на локально подписанных токенах с подставным транспортом сертификатов.
- **Выключение.** Пустой `GOOGLE_CLIENT_ID` → `providers` отдаёт `google_client_id: null`, `POST /auth/google` — `503 google_login_unavailable` без обращения к Google.
- **Аккаунт ищется только по `google_sub`.** Если его нет — создаётся новый **пассажир**: `google_sub`, `email`, `password_hash = NULL`, username из части email до `@` (нижний регистр, символы вне `[a-z0-9_]` → `_`, короче 3 символов — с `_user`, не длиннее 32; при занятом имени — `_2` … `_20`, затем случайный суффикс). `name` из токена становится `display_name` нового профиля. Существующие аккаунты (в том числе водитель или admin с тем же email или username) никогда не связываются: email не даёт прав, роль Google-пользователя — всегда `passenger`. Одновременный первый вход тем же `sub` даёт одного пользователя (повторный поиск внутри записи и уникальный индекс; при `IntegrityError` — до трёх попыток).
- **Пароль.** Для Google-аккаунта `password_hash IS NULL`; обычный login проверяет dummy-хеш и отвечает `401 invalid_credentials`, как для неизвестного username.
- **Origin и сессия как у login.** `POST /auth/google` проверяется `require_allowed_origin`; присланная cookie прежней сессии отзывается в транзакции новой.
- **Ограничитель.** Отдельный экземпляр `LoginAttemptLimiter` с теми же настройками (`LOGIN_MAX_ATTEMPTS` за `LOGIN_ATTEMPT_WINDOW_SECONDS`), ключ — Google `sub`, учитывается после успешной проверки подписи, без сброса при успехе: не больше 5 входов одного Google-аккаунта за 15 минут. Ключ нельзя подделать без настоящего токена этого аккаунта, поэтому чужой аккаунт так не заблокировать; отдельный экземпляр не даёт парольному входу с username `google:…` или `<sub>` занять счётчик Google.

## Схема

Миграция `a7c41e9d3b58` меняет только `users`: `google_sub` (nullable, `uq_users_google_sub`), `email` (nullable, без уникальности), `password_hash` становится nullable, `ck_users_has_credentials`: `password_hash IS NOT NULL OR google_sub IS NOT NULL`. SQLite перестраивает таблицу в batch-режиме; существующие аккаунты не меняются. Downgrade с потерей данных: колонки удаляются, Google-аккаунтам ставится непригодный хеш `!` (вход по паролю невозможен), строки и ссылки на них сохраняются.

## Ограничения

- Реальный вход с настоящим Client ID — **external_pending**: Client ID ещё не выдан, проверены только детерминированные тесты.
- Сертификаты Google не кэшируются: каждая попытка (и каждый мусорный токен) — один исходящий запрос. Недействительные токены ограничителем не считаются (их `sub` не проверен). Для локального MVP принято.
- Ограничитель в памяти процесса (ADR 0003); при частых повторных входах одним аккаунтом (например, при разработке фронтенда) шестой вход за 15 минут получит `429`.
- Связывания Google с существующим локальным аккаунтом и входа водителей/admin через Google нет; email не проверяется на уникальность и не меняется при следующих входах.
- Отзыв доступа в Google не завершает уже выданную сессию — она живёт до logout или 7 дней.
