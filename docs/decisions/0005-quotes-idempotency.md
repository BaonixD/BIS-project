# ADR 0005: Quote поездки и идемпотентное создание

Дата: 3 ноября 2026 года. Статус: принято для реализации T05.

## Контекст

MVP_SPEC §5–§6: сервер сам считает цену по дорожному маршруту, хранит quote 5 минут, поездка создаётся только из собственного непросроченного quote, у пассажира не больше одной активной поездки, `Idempotency-Key` обязателен, повтор того же ключа и тела возвращает тот же результат, другой payload — 409. Внешний маршрутный запрос не должен держать транзакцию (ADR 0001, 0002).

## Решение

### Quote

- `POST /api/v1/rides/quotes`, только `passenger`. Маршрут — `plan_road_route` вне транзакции и без занятого соединения БД, затем `calculate_fare` (`edu-v1`) и одна короткая `session.begin()` с INSERT. Ошибки маршрутизации (`503 routing_unavailable`, `503 routing_provider_error`, `422 route_not_found`, `422 route_points_identical`) проходят без изменений, quote не создаётся.
- `ride_quotes` хранит владельца, точки, метры, секунды, GeoJSON, провайдера, `amount_kzt`, `KZT`, `tariff_version`, `created_at` и `expires_at = created_at + 5 мин` по `Clock`. Время берётся после ответа провайдера: 5 минут — это время пассажира на решение.
- Quote истёк при `now >= expires_at` (граница включительно, как у предложений водителю).
- Quote не идемпотентен: повтор создаёт новый quote. Это безопасно — quote ничего не резервирует. Неиспользованные quote остаются в таблице; очистка — будущая задача.

### Снимок цены

Поездка копирует из quote маршрут, сумму, валюту и `tariff_version` (`Ride.from_quote`). Сумма из тела не принимается: тело `POST /rides` — только `quote_id`, `extra="forbid"` (лишние поля → `422 validation_error`). Изменение тарифа влияет только на новые quote; сохранённые quote и поездки не пересчитываются.

### Создание поездки

`POST /api/v1/rides`, только `passenger`, заголовок `Idempotency-Key` обязателен. Всё в одной пишущей транзакции (`BEGIN IMMEDIATE` на SQLite), в таком порядке:

1. Запись `(user_id, "create_ride", key)` уже есть: тот же fingerprint → вернуть ту же поездку; другой → `409 idempotency_key_reused`. Проверки quote после этого не выполняются: повтор отвечает и после истечения quote.
2. Quote не найден или чужой → `404 quote_not_found` (одинаково, без details).
3. Из quote уже создана поездка → `409 quote_already_used`.
4. `now >= expires_at` → `409 quote_expired`.
5. У пассажира есть поездка в `searching/assigned/arrived/in_progress` → `409 active_ride_exists`.
6. INSERT поездки (`searching`, `driver_id = NULL`) и записи идемпотентности.

Записывается только успешное создание: ошибка откатывает транзакцию и ключ не резервирует (повтор с тем же ключом выполняется заново).

### Ответ на повтор

Первый запрос и повтор отвечают `201` с текущим состоянием той же поездки (не сохранённой копией первого ответа: статус мог измениться). У повтора есть заголовок `Idempotent-Replayed: true`. CORS пропускает `Idempotency-Key` и открывает `Idempotent-Replayed`.

### Ключ и fingerprint

- Ключ: 1–128 видимых ASCII-символов `0x21–0x7E` (без пробелов). Нет заголовка → `422 idempotency_key_required`; неверный формат → `422 idempotency_key_invalid` (значение в ответ не возвращается). 422, а не 400, — по MVP_SPEC §3 «некорректные поля».
- Область — пользователь и операция: одинаковый ключ у разных пассажиров не конфликтует.
- `request_fingerprint` — SHA-256 (hex) канонического JSON уже проверенного тела: `model_dump(mode="json")`, ключи отсортированы, без пробелов, UTF-8. Разное написание одного UUID даёт один fingerprint.

### Ограничения БД и гонки

- `rides.quote_id` UNIQUE; partial unique index `uq_rides_active_passenger_id` по `passenger_id` при `status IN (searching, assigned, arrived, in_progress)`; `idempotency_records` UNIQUE `(user_id, operation, key)`. Индексы объявлены с `sqlite_where` и `postgresql_where`.
- На SQLite пишущие транзакции сериализованы, поэтому проверки Python видят результат конкурента. На PostgreSQL (READ COMMITTED) обе транзакции могут пройти проверки; тогда отказывает ограничение. `IntegrityError` не превращается в 500: в новой read-транзакции по зафиксированным строкам победителя ответ выводится заново — повтор, `idempotency_key_reused`, `quote_already_used` или `active_ride_exists`; иначе исходная ошибка. Тесты эмулируют устаревшие проверки подменой первого вызова pre-check в репозитории.
- Водитель: `uq_rides_active_driver_id` по `driver_id` при `status IN (assigned, arrived, in_progress)` — не больше одной принятой активной поездки (используется в T06/T07).
- `ck_rides_driver_matches_status`: `searching`/`no_driver` — без водителя; `assigned`/`arrived`/`in_progress`/`completed` — с водителем; `cancelled` — любой вариант, потому что отмена возможна до и после назначения. После `release` поездка снова `searching`, значит `driver_id` обязан очиститься. Это самый строгий CHECK, не запрещающий допустимых переходов MVP_SPEC §6.
- `rides.driver_id` ссылается на `driver_profiles.user_id`: назначить можно только пользователя с профилем водителя.

### Доступ к поездке

`GET /api/v1/rides/{id}` (read_transaction): пассажир поездки, водитель из `rides.driver_id` (после release доступ пропадает) и admin. Остальные и несуществующий id — `404 ride_not_found` без details.

### Хранение записей идемпотентности

Повтор гарантирован не меньше 24 часов. Очистка — будущая задача (удаление строк старше 24 ч); до неё записи хранятся бессрочно, то есть ключ остаётся занятым. `resource_id` не внешний ключ: таблица общая для будущих операций.

## Последствия и ограничения

- Назначения водителя в T05 нет; поиск и предложения — T06.
- Поведение на PostgreSQL не проверялось (ADR 0001); переносимость частичных индексов проверена компиляцией DDL.
- Срок quote (5 мин) и правила ключа — константы кода, не настройки.
- Нет фоновой очистки quote и записей идемпотентности.
