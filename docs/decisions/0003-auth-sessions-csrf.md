# ADR 0003: Серверные сессии, CSRF, Origin и CORS

Дата: 3 ноября 2026 года. Статус: принято для реализации T02.

## Контекст

MVP_SPEC §4 требует вход по username/password для монолита и будущего React-клиента, HttpOnly cookie, CSRF-защиту изменяющих запросов, проверку Origin для входа и регистрации, CORS-allowlist и простой ограничитель перебора без Redis. Swagger и HTTPX должны проходить сценарий без фронтенда.

## Решение

### Сессии вместо JWT

- Серверная сессия — строка `auth_sessions`. Клиент получает случайный токен (`secrets.token_urlsafe(32)`, 256 бит) в cookie `taxi_session`; в БД хранится только `sha256(token)` (`token_hash`, уникальный). Копия БД не даёт войти.
- Срок — 7 дней по часам сервера (`expires_at = created_at + 7 дней`, `Clock` приложения). Сессия действует, пока `revoked_at IS NULL` и `expires_at > now`; иначе `401 not_authenticated`.
- `POST /auth/logout` ставит `revoked_at` (условный `UPDATE`) и удаляет cookie. Новый вход с уже присланной cookie отзывает прежнюю сессию в той же транзакции — у браузера не остаётся двух рабочих сессий или сессии предыдущего пользователя. Сессии других браузеров не затрагиваются.
- Почему не JWT: отзыв и истечение должны работать сразу и проверяться в БД; JWT потребовал бы списка отзыва и refresh-слоя. Один запрос по уникальному индексу на запрос дешевле для локального монолита.
- Хеш пароля — Argon2id через `argon2-cffi` (RFC 9106 low-memory: t=3, 64 MiB, p=4; параметры в настройках, тесты используют минимальные). Хеширование и проверка выполняются в потоке, вне event loop и вне транзакции. Для неизвестного username выполняется проверка против dummy-хеша той же стоимости; ответ одинаковый (`401 invalid_credentials`).

### Cookie

| Атрибут | Значение | Зачем |
| --- | --- | --- |
| `HttpOnly` | всегда | токен недоступен JavaScript (XSS не крадёт сессию) |
| `SameSite=Lax` | всегда | браузер не шлёт cookie в межсайтовых POST/fetch; переходы по ссылкам работают |
| `Secure` | `SESSION_COOKIE_SECURE`, по умолчанию `true` | только HTTPS; для локального `http://localhost` в `.env.example` явно `false` |
| `Path=/`, `Max-Age` 7 дней | всегда | срок cookie совпадает со сроком сессии |

### CSRF

- Синхронизирующий токен на сессию: случайный `csrf_token` хранится в строке сессии и выдаётся аутентифицированному клиенту в `GET /auth/session` (и в ответе login). Без cookie он бесполезен, поэтому хранится как есть.
- `CurrentUser` для всех методов, кроме GET/HEAD/OPTIONS, требует заголовок `X-CSRF-Token`, равный токену именно этой сессии (сравнение за постоянное время); иначе `403 csrf_failed`. Любой маршрут с `CurrentUser`/`require_roles` защищён без дополнительного кода. Токен другой или отозванной сессии не подходит; после logout и нового входа выдаётся новый.
- Заголовок нельзя выставить межсайтовой HTML-формой, а межсайтовый `fetch` с ним требует CORS-preflight, который пройдёт только для allowlist.
- GET-маршруты не должны менять состояние.
- При включённом SQL-логировании `csrf_token` виден в INSERT сессии. Без cookie сессии он бесполезен, поэтому это принято; SQL-логирование в обычном запуске выключено.

### Origin для login/register

- У входа и регистрации ещё нет сессии и CSRF-токена. Защита — проверка `Origin`: допустимы origin из `CORS_ALLOWED_ORIGINS` и собственный origin API (схема + `Host`, нужен Swagger UI на том же хосте). Остальное, включая `null`, — `403 origin_not_allowed` до обработки тела.
- Запрос без `Origin` допускается: так работают curl, HTTPX и серверные клиенты. Браузеры отправляют `Origin` со всеми межсайтовыми POST, поэтому атака через браузер жертвы заголовок содержит. Это защищает от login CSRF (вход жертвы под чужим аккаунтом).

### CORS

- `CORSMiddleware` с `allow_origins = CORS_ALLOWED_ORIGINS`, `allow_credentials=True`, методами GET/POST/PUT/PATCH/DELETE, заголовками `Content-Type`, `X-CSRF-Token`, `X-Request-ID`; `X-Request-ID` открыт клиенту. Origin нормализуются (нижний регистр, без порта по умолчанию); `*`, `null`, пути и учётные данные в URL отклоняются при загрузке настроек — credentials никогда не сочетаются с wildcard. Пустой список (по умолчанию) — межсайтовый доступ закрыт.

### Ограничитель перебора входа

- In-memory `LoginAttemptLimiter`: не больше `LOGIN_MAX_ATTEMPTS` (5) попыток на нормализованный username в скользящем окне `LOGIN_ATTEMPT_WINDOW_SECONDS` (900 с) по часам приложения. Учитывается каждая попытка, успешный вход сбрасывает счётчик; сверх лимита — `429 too_many_attempts` с `details.retry_after_seconds`, даже при верном пароле. Неизвестные username ограничиваются так же.
- Память ограничена: не больше `LOGIN_LIMITER_MAX_KEYS` (10 000) ключей и `max_attempts` отметок на ключ; при заполнении сначала удаляются ключи без попыток в окне, затем наименее недавно использованный.

### Роли

- Публичная регистрация — только `passenger`/`driver`; `role=admin` даёт `422 validation_error` (значение вне допустимого перечня), пользователь не создаётся. Admin создаётся локальной командой `scripts/create_admin.py` (пароль из `ADMIN_PASSWORD` или `getpass`).
- `require_roles(...)` возвращает `403 forbidden` для других ролей после проверки сессии и CSRF. Права на конкретный объект проверяют сервисы.

## Ограничения

- Состояние ограничителя теряется при перезапуске и не разделяется между процессами; запуск в несколько воркеров ослабляет лимит. Для локального однопроцессного MVP это принято (Redis вне границ).
- Ключ ограничителя — username: перебор пароля одного аккаунта ограничен, но кто угодно может временно заблокировать вход чужого аккаунта (до 15 минут). Перебор по многим username с одного адреса не ограничивается. Поток из `LOGIN_LIMITER_MAX_KEYS` новых username вытесняет старые ключи и сбрасывает их счётчики.
- Одновременно выполняются не более двух операций Argon2id на приложение (semaphore), остальные ждут: память ограничена, но всплеск входов увеличивает задержку. Engine создаётся с `hide_parameters=True`, поэтому параметры SQL (например, хеш пароля) не попадают в текст ошибок и логи.
- Истёкшие и отозванные строки `auth_sessions` не удаляются автоматически; очистка — будущая задача обслуживания.
- Хеш пароля не пересчитывается при изменении параметров Argon2id (rehash при входе не реализован).
- Проверка собственного origin опирается на `Host`; за обратным прокси с другой схемой потребуется явный allowlist.
- Сравнение времени проверки пароля для известного и неизвестного username сопоставимо, но не гарантирует постоянства (кэш, ограничитель, запросы к БД).
