# ADR 0004: Оплата — наличные по умолчанию и Kaspi по ссылке с ручной сверкой

Дата: 3 ноября 2026 года. Статус: принято для T08 часть A (чистые правила и Kaspi-ссылка) и часть B (хранение, аудит, API, открытие при завершении поездки — раздел «Хранение и аудит»).

## Контекст

BACKEND_PLAN §7 и MVP_SPEC §7: оплата отделена от поездки, наличные — основной способ, Kaspi — по ссылке владельца. Владелец получил ссылку точки продаж на хосте `pay.kaspi.kz`. По [Kaspi Гиду](https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2098) по такой ссылке покупатель сам вводит сумму, а кассир получает уведомление в мобильном POS. API для проверки оплаты конкретной поездки и параметр суммы в ссылке не подтверждены.

## Решение

- Новая запись оплаты: `method=cash`, `status=unpaid`. Методы: `cash`, `kaspi_link`. Статусы: `unpaid`, `reported`, `confirmed`. Верификация всегда `manual`.
- Kaspi — обычная ссылка точки продаж из `KASPI_PAYMENT_URL`. Покупатель вводит сумму вручную; сервер показывает сумму поездки из серверного снимка (целое KZT) и ссылку. QR строит фронтенд из этой ссылки.
- Сумма и любые другие параметры в ссылку не подставляются: формат deeplink неизвестен, параметры не выдумываются.
- Подтверждение только ручное. Webhook и автоподтверждения нет: у обычной ссылки нет подтверждённого протокола уведомлений или запроса статуса. Обещать автоматическую сверку без такого протокола было бы ложью.
- «Я оплатил» (`report`) переводит `unpaid → reported` и означает только заявление пассажира. Открытие ссылки, сканирование QR и возврат из приложения статус не меняют.

## Переходы

| Действие | Из | В | Примечание |
| --- | --- | --- | --- |
| report | kaspi_link/unpaid | reported | повтор на reported — без изменений |
| confirm | cash/unpaid, kaspi_link/unpaid, kaspi_link/reported | confirmed | повтор на confirmed — «уже подтверждено» (`changed=false`), без второго начисления и без ошибки |
| change_method | unpaid/reported, другой метод | новый метод, unpaid | только до confirmed; на kaspi_link — только при настроенной ссылке; тот же метод — без изменений |

Остальные сочетания — 409 `invalid_payment_transition` с `action`, `method`, `status` в `details`. В частности, report для cash запрещён. Переход с Kaspi на cash сбрасывает заявление `reported` в `unpaid`, потому что у наличных нет заявления пассажира. Подтверждённый платёж смена метода не трогает.

## Права

Проверка идёт в порядке: видимость, право роли, завершённость поездки.

| Действие | Кто | Ошибки |
| --- | --- | --- |
| report, change_method | пассажир поездки | |
| confirm cash | назначенный водитель или admin | |
| confirm kaspi_link | только admin, обязательна заметка/reference ручной сверки с POS | |
| любое | посторонний пассажир или водитель | 404 `ride_not_found`, как в правилах поездки |
| любое | участник без права, в том числе admin для report/change_method | 403 `payment_action_forbidden` |
| любое разрешённое | поездка ещё не completed | 409 `ride_not_completed` |

Флаги участника учитываются только вместе с соответствующей ролью. Заметка обрезается по краям, длина не больше 200 символов, без управляющих, форматирующих (bidi, zero-width) символов и разрывов строк. Для Kaspi пустая заметка даёт 422 `confirmation_reference_required`, некорректная — 422 `invalid_confirmation_reference`. Для cash заметка необязательна. Заметка не должна содержать секретов: это правило для оператора, автоматически его проверить нельзя.

## Ссылка Kaspi

- Источник — только `KASPI_PAYMENT_URL` (`PaymentSettings`, без префикса). Ссылка хранится в локальном `.env` владельца и не попадает в Git; в `.env.example` поле пустое. Из тела клиента URL не принимается: в сборке инструкций нет параметра URL, есть только настройки.
- Допустима только форма `https://pay.kaspi.kz/pay/<id>`, где `<id>` — от 1 до 64 символов `[A-Za-z0-9_-]`. Хост сравнивается строго: без поддоменов и обманок вида `pay.kaspi.kz.evil.com`, без userinfo, порта (включая `:443`), завершающей точки, query и fragment. Разрешены только ASCII-символы без пробелов.
- Пустое или отсутствующее значение выключает Kaspi: наличные работают, переход на kaspi_link даёт 503 `kaspi_unavailable` (MVP_SPEC §3: недоступная внешняя возможность, как `routing_unavailable`). Недопустимое значение вызывает ошибку конфигурации при загрузке настроек; само значение в сообщение не попадает (`hide_input_in_errors`).
- Ссылка выдаётся только для kaspi_link в статусах unpaid или reported. Для confirmed она скрыта, чтобы не спровоцировать повторную оплату. Если Kaspi выключили после выбора, report и confirm остаются доступны для сверки уже сделанного платежа, а ссылка не выдаётся.
- Реальная ссылка владельца проходит валидатор. Проверка без сетевого запроса и без вывода значения выполнена в рамках T08A. Открытие ссылки и реальная оплата — `external_pending`.
- `PaymentSettings` создаётся один раз в `create_app` (параметр `payment_settings` или окружение/`.env`) и внедряется в маршруты зависимостью из `app.state`. Тесты передают контролируемые настройки (`https://pay.kaspi.kz/pay/test123` либо без ссылки) и обнуляют `KASPI_PAYMENT_URL`, как `ROUTING_*`.

## Хранение и аудит (часть B)

### Запись оплаты `payments`

Одна строка на поездку (`UNIQUE ride_id`): `amount_kzt` (копия суммы поездки, `> 0`), `currency = 'KZT'`, `method`, `status`, `verification = 'manual'`, `reported_at`, `confirmed_at`, `confirmed_by` (FK users), `confirmation_reference`, `created_at`, `updated_at`. Сумма после открытия не меняется: её не принимает ни одна команда.

CHECK-ограничения дублируют правила в БД минимально строго:

- `confirmed` ⇔ заданы `confirmed_at` и `confirmed_by`; вне `confirmed` нет и `confirmation_reference`;
- `unpaid` — без `reported_at`, `reported` — с ним; `reported_at` бывает только у `kaspi_link` (смена метода на cash его очищает);
- подтверждённый `kaspi_link` обязательно имеет `confirmation_reference`; длина заметки 1–200.

`confirmed` Kaspi без предварительного `report` допустим (admin сверил POS сам), поэтому `reported_at` у `confirmed` не обязателен.

### Открытие при завершении

Хук T07 `on_ride_completed(session, ride, now)` вызывает `open_payment`: в транзакции `complete` добавляет `cash`/`unpaid` с суммой из снимка поездки и событие `open`, без commit и без внешних ожиданий. Ошибка вставки (в том числе нарушение `UNIQUE ride_id`) откатывает и завершение — поездка остаётся `in_progress`. Повторный `complete` хук не вызывает.

Миграция `272671ab4753` открывает такие же записи (и события `open` со временем `completed_at`) для поездок, завершённых до неё, чтобы у каждой завершённой поездки была оплата. Откат удаляет обе таблицы вместе с данными.

### Команды и аудит `payment_events`

Каждая команда — одна транзакция: блокировка поездки, затем её оплаты (`rides → payments`, `with_for_update`), `authorize_payment_action`, чистое правило (`apply_method_change`, `apply_report`, `apply_confirm`), изменение строки и событие. Если правило вернуло `changed=false`, строка и аудит не меняются, ответ — `200` с `changed: false`. Две конкурентные подтверждающие команды сериализуются блокировкой: вторая видит `confirmed` и события не пишет.

Событие: `action` (`open`, `change_method`, `report`, `confirm`), `from_status`/`to_status`, `from_method`/`to_method` (у `open` предыдущего состояния нет), `actor_id` (`NULL` только у системного `open`), `reference` (только у `confirm`), `created_at`. Аудируются каждое значимое изменение и каждое ручное подтверждение; события не удаляются.

### API

- `GET /rides/{id}/payment` — инструкции `build_payment_instructions` и состояние; видят пассажир, назначенный водитель и admin. До завершения — `409 ride_not_completed`: записи ещё нет, а код совпадает с ответом команд (выбран вместо `404 payment_not_found`, чтобы не путать с чужой поездкой). `404 payment_not_found` остаётся защитой для завершённой поездки без записи.
- `PUT /rides/{id}/payment/method`, `POST .../report`, `POST .../confirm` — тела с `extra=forbid`: сумма, ссылка, статус и verification из тела не принимаются (`422`).
- Заметка проверяется после прав и до правила перехода, как любое входное поле: повтор подтверждения Kaspi без заметки тоже `422`, а с заметкой — `200`, `changed: false`, исходные `confirmed_by`/`confirmation_reference` сохраняются.
- `confirmation_reference` в ответе видит только admin; остальным — `null`.
- `RideSummary` истории и `GET /admin/rides` содержит `payment_status`, `payment_method` (одним `LEFT JOIN`, `null` до завершения).

## Последствия

- Часть B хранит одну запись оплаты на поездку и аудирует каждое подтверждение и смену метода: актор, время, метод, reference. Повторное подтверждение аудит не дублирует.
- Ручная сверка — операционная нагрузка admin, и это осознанный выбор для MVP. Автоматическая сверка возможна только через отдельно документированную интеграцию Kaspi, если она станет доступна.
- Возвраты, эквайринг и webhooks вне объёма.
