# ADR 0007: Жизненный цикл поездки — команды, история, гонки и точка завершения

Дата: 3 ноября 2026 года. Статус: принято для реализации T07 часть B.

## Контекст

MVP_SPEC §6: назначенный водитель отмечает arrived, start, complete; пассажир отменяет поездку до `in_progress`; водитель до начала может освободить назначение с причиной — поездка возвращается в `searching` с новым 180-секундным поиском без него. Завершение освобождает водителя и открывает запись неоплаченной стоимости (§7, T08). Устаревшие координаты не завершают и не отменяют поездку. Правила переходов и прав — чистые функции `states.py` (T07 часть A); транзакции — ADR 0001; поиск и предложения — ADR 0006.

## Решение

### Команды

`POST /api/v1/rides/{id}/arrive | start | complete | cancel | release`, сессия и `X-CSRF-Token` (общая зависимость `CurrentUser`). Ответ — `RideResponse` с текущим состоянием.

| Команда | Кто | Из | В | Тело |
| --- | --- | --- | --- | --- |
| arrive | назначенный водитель | assigned | arrived | — |
| start | назначенный водитель | arrived | in_progress | — |
| complete | назначенный водитель | in_progress | completed | — |
| cancel | пассажир поездки | searching, assigned, arrived | cancelled | необязательно `{"reason"}` |
| release | назначенный водитель | assigned, arrived | searching | обязательно `{"reason"}` |

Причина — текст 1–200 символов после обрезки пробелов, без управляющих символов (Unicode `Cc`), лишние поля тела — `422 validation_error`. Перечисление причин не вводилось: для учебного MVP текст полезнее, ограничение длины и символов защищает журнал.

### Порядок проверки (одна транзакция на команду)

1. `SELECT ... FOR UPDATE` поездки (`transitions.lock_ride`; на SQLite — `BEGIN IMMEDIATE`). Нет строки — `404 ride_not_found`.
2. `Actor` из строки поездки и роли пользователя: пассажир — `passenger_id`, назначенный водитель — `driver_id`.
3. `resolve_command`: не участник и не admin — `404 ride_not_found`; участник или admin без права — `403 ride_command_forbidden` (admin жизненным циклом не управляет); уже применённая идемпотентная команда (arrive на arrived, start на in_progress, complete на completed, cancel на cancelled) — `200` с текущим состоянием, без эффектов и без события; иначе переход по таблице или `409 invalid_ride_transition` (`details.current_status`, `details.command`). `release` не идемпотентен: после release водитель уже не участник (`404`).
4. `transitions.move_ride`: условный `UPDATE rides ... WHERE id = ? AND status = <прочитанный>` со временем этапа и строка `ride_events` — вместе. Под блокировкой промах невозможен; если он всё же случится, это `409`, а не тихая запись.
5. Эффекты в той же транзакции: cancel — `revoke_pending_offers` (порядок блокировок rides → ride_offers); release — `driver_id = NULL`, `assigned_at`/`arrived_at = NULL`, `restart_search` (новое окно строго позже прежнего, `deadline = start + 180 с`); complete — хук завершения.

После коммита release выполняется первый шаг поиска через `dispatch.start_search`: сбой шага логируется, ответ остаётся `200` с поездкой `searching`, поиск продолжит фоновый цикл. Ответ release — снимок, зафиксированный самим release (`searching`, `driver_id = null`), либо `no_driver`, если именно этот поиск (то же `search_started_at`) сразу никого не нашёл. Освободивший водитель больше не участник (MVP_SPEC §3), поэтому изменения, сделанные другими между коммитом release и ответом (отмена пассажира с причиной, принятие следующим водителем), в ответ не попадают (ревью T07B). Освободивший водитель исключён из всех будущих поисков этой поездки (его `accepted` предложение, ADR 0006).

### Данные

- `rides`: `assigned_at`, `arrived_at`, `started_at`, `completed_at`, `cancelled_at` (UTC, nullable) и `cancel_reason` (≤ 200). `assigned_at` ставит accept (T06). Отмена после назначения сохраняет `driver_id` как историю: частичный индекс `uq_rides_active_driver_id` и фильтр кандидатов смотрят только `assigned/arrived/in_progress`, поэтому водитель свободен сразу.
- `ride_events`: `ride_id`, `from_status`, `to_status`, `command`, `actor_id` (пользователь, вызвавший переход; для `assign` — принявший водитель; `NULL` — фоновый цикл и `mark_no_driver`), `reason`, `created_at`; CHECK статусов, команд и длины причины; индекс `(ride_id, created_at, id)`. Координат, телефонов и секретов нет.
- Каждый переход пишет событие через одну функцию `move_ride`: команды T07B и пути T06 (accept → `assign`, шаг поиска → `mark_no_driver`). Создание поездки событием не считается (это не переход; время — `rides.created_at`).
- Ревизия `b42082a5b952` от `5d2e4cb65b5e`: новые столбцы `rides` добавляются без пересоздания таблицы; у существующих поездок они `NULL`. CHECK на согласованность времени и статуса в `rides` не добавлен: потребовалось бы пересоздание таблицы и заполнение истории, которой нет; длина `cancel_reason` проверяется API. Downgrade пересоздаёт `rides` в batch-режиме и сохраняет CHECK и частичные индексы (тест).

### Accept по отменённой поездке

Решение ревью T06: accept предложения, чья поездка уже `cancelled`, — всегда `409 invalid_ride_transition` (`current_status: cancelled`, `command: assign`), независимо от статуса предложения: повтор уже принятого предложения после отмены пассажиром и принятие отозванного при отмене предложения отвечают одинаково. Повтор accept по завершённой этим водителем поездке по-прежнему возвращает её (прежний успешный результат, ADR 0006).

### Гонки

Все команды и dispatch блокируют поездку первой; на SQLite пишущие транзакции сериализованы. Проверено конкурентными тестами (по 2 запроса):

- accept против cancel: поездка всегда `cancelled`; либо `[assign, cancel]` и предложение `accepted`, либо accept — `409 invalid_ride_transition`, `[cancel]` и предложение `revoked`;
- start против cancel: ровно один `200`, второй `409`; история заканчивается командой победителя;
- complete против complete: оба `200`, одно событие `complete`, хук вызван один раз;
- release против cancel: три допустимых исхода, статус всегда равен `to_status` последнего события, висящих предложений нет.

### Водитель во время поездки

Пока у водителя поездка `assigned/arrived/in_progress`, `PUT /drivers/me/availability {"online": false}` и любой `PATCH /drivers/me` (ФИО, телефон, удостоверение, машина) — `409 driver_on_active_ride`: пассажир видит эти данные в карточке, а офлайн-водитель с поездкой противоречил бы назначению. Координаты обновляются как обычно. Проверка — после блокировки профиля (`FOR NO KEY UPDATE`), чтение `rides` без блокировки, поэтому цикла блокировок с командами нет.

### Карточка водителя и устаревшие координаты

`GET /rides/{id}` отвечает `RideDetailsResponse` = `RideResponse` + `driver`. Пока поездка `assigned/arrived/in_progress`, её пассажир и назначенный водитель получают `driver`: `full_name`, `phone`, машина (`make`, `model`, `color`, `plate_number`), последняя координата и `location_updated_at` из `driver_profiles`. Admin, другие статусы — `driver: null`; посторонние — `404`. Истории координат нет. Ни цикл, ни команды не смотрят на возраст координаты принятой поездки: клиент показывает время последнего обновления, поездка не завершается и не отменяется. Команды и списки карточку не возвращают — её получают опросом `GET /rides/{id}`.

### Контракт завершения для T08B

`modules/rides/lifecycle.py`:

```python
CompletionHook = Callable[[AsyncSession, Ride, datetime], Awaitable[None]]
async def on_ride_completed(db: AsyncSession, ride: Ride, now: datetime) -> None: ...
```

- `create_app` кладёт хук в `app.state.ride_completion_hook` (по умолчанию `on_ride_completed`; с T08 часть B открывает cash/unpaid-оплату и событие `open` в той же транзакции, ADR 0004); `lifecycle.execute_command(..., on_completed=...)` получает его через зависимость `CompletionHookDep` (`rides/dependencies.py`). Тесты подменяют `app.state.ride_completion_hook`.
- Вызывается ровно один раз на поездку — только при реальном переходе `in_progress → completed`, внутри транзакции complete, после `UPDATE` и события: `ride.status == completed`, `ride.completed_at == now`, `ride.amount_kzt` — зафиксированная цена; строка поездки заблокирована. Повтор complete хук не вызывает.
- Всё, что хук записал через `session`, коммитится вместе с завершением; исключение откатывает и завершение (поездка остаётся `in_progress`, клиент получает `500`/доменную ошибку). Хук не коммитит, не открывает новую транзакцию и не ждёт внешних вызовов.
- T08B: в `on_ride_completed` (или своей функции, назначенной в `create_app`) добавить `Payment(ride_id=ride.id, amount_kzt=ride.amount_kzt, method=cash, status=unpaid, created_at=now)` через `session.add` + `flush`; `UNIQUE(payments.ride_id)` — защита от второй записи. Фальшивых подтверждений нет.

## Ограничения

- PostgreSQL не проверялся (ADR 0001): блокирующие `SELECT` скомпилированы для PostgreSQL в тестах порядка блокировок. При READ COMMITTED проверка «водитель на поездке» в пути водителя не видит незакоммиченный accept: водитель может уйти offline в момент принятия; двойного назначения это не даёт. Конкурентные тесты на SQLite доказывают сериализацию, а не пересечение транзакций.
- Порядок событий одной поездки — `created_at`, затем `id`; при равном времени (возможно лишь с замороженными тестовыми часами) порядок по `id` произвольный, тесты используют порядок вставки SQLite.
- Нет аварийного закрытия `in_progress`, споров и штрафов (MVP_SPEC §6); нет WebSocket — клиенты опрашивают `GET /rides/{id}`.
- Старые события не чистятся.
