# Оркестрация разработки Mini Taxi Service

Дата: 2 ноября 2026 года.

Связанный документ: [BACKEND_PLAN.md](BACKEND_PLAN.md).

## 1. Назначение и текущий статус

Этот документ определяет, как оркестратор уточняет требования, делегирует работу, изолирует исполнителей, проверяет результаты и объединяет изменения.

**Подготовлен пакет исполнения для Claude Code: [CLAUDE_START.md](CLAUDE_START.md), [docs/TASKS.md](docs/TASKS.md) и карточки задач. Здесь выполняется подготовка репозитория; реализация запускается пользователем в Claude готовым промптом.**

Желаемое распределение ролей пользователя:

- Astra 6 — оркестратор.
- Opus 5.5 — основной исполнитель реализации.
- Пользователь — владелец продукта и источник решений о функциях, приоритетах и допустимых упрощениях.

Пять участников учебной команды и их Student ID перечислены в `BACKEND_PLAN.md`. Их роли пользователь сообщит позже. Роли AI-исполнителей не подменяют распределение работы между участниками команды.

Выбран способ передачи через Git-репозиторий и Claude Code. Корневой `CLAUDE.md` задаёт правила, `docs/TASKS.md` — очередь, `.claude/agents/` — исполнителя и ревьюера на `claude-opus-5-5`. Доступ к модели в аккаунте пользователя и её фактический запуск этим документом не подтверждаются. Если модель недоступна, Claude сообщает об этом и не выдаёт другую модель за Opus 5.5.

### Автономный проход в Claude

Astra готовит спецификацию и делегирование. Главная сессия Claude после запуска исполняет подготовленную очередь, выполняет техническую координацию и собирает результат в `integration/backend-mvp`. Ей не нужно ждать ответа Astra после каждой задачи. Независимый ревьюер Claude проверяет отдельные задачи; итоговое ревью Astra выполняется после передачи готового результата.

В этом режиме Claude разрешено создавать локальные ветки/worktree, делать коммиты и сливать проверенные задачи в integration-ветку. При отсутствии отдельного ревьюера последовательная реализация разрешена, но в отчёте указывается самопроверка. `main` остаётся базой подготовленного пакета до итогового принятия; готовность к ревью не выдаётся за уже состоявшуюся приёмку Astra.

## 2. Обязательные ограничения

- Модульный монолит на FastAPI, PostgreSQL и PostGIS.
- Текущий этап — бэкенд. Для финальной защиты нужен готовый интерфейс; фронтенд планируется позже, мобильное приложение остаётся необязательным.
- Локальный запуск, без CI, микросервисов и Kafka.
- Новая инфраструктура не добавляется без предметного обоснования и согласования.
- Исполнитель не расширяет задачу самостоятельно.
- Рабочие допущения берутся только из `docs/MVP_SPEC.md` и явно обозначаются как решения оркестратора. Исполнитель не придумывает новые противоречащие им бизнес-правила.
- Результат оценивается по критериям приёмки и проверкам, а не по заявлению исполнителя «готово».
- Рабочие изменения пользователя сохраняются; чужие ветки, файлы и БД не сбрасываются и не очищаются.

Согласованные продуктовые решения берутся из актуального `BACKEND_PLAN.md`: Алматы/KZT, username/password, Google позже, реальные дорожные маршруты, ближайший водитель с подтверждением, 30 секунд на ответ и переход к следующему, наличные и подготовка Kaspi по ссылке пользователя. Эти решения не пересматриваются исполнителями без основания.

Ссылка Kaspi и доступ к маршрутизации — внешние зависимости конкретных задач. Их отсутствие не блокирует независимые задачи. Исполнитель не покупает тарифы, не регистрирует коммерческие интеграции и не принимает реальные платежи в рамках обычной разработки.

## 3. Ответственность участников

### Оркестратор

1. Проводит опрос, фиксирует ответы и отличает требования от предложений.
2. Поддерживает актуальность `BACKEND_PLAN.md`.
3. Разбивает работу на задачи с понятным результатом и зависимостями.
4. Согласует общие контракты, владельцев файлов и порядок миграций до параллельного запуска.
5. Назначает исполнителю отдельную ветку, рабочую копию и тестовое окружение.
6. Отслеживает блокировки и изменения контрактов.
7. Проверяет код и доказательства выполнения, возвращает конкретные замечания.
8. Интегрирует принятые изменения и проверяет итоговую совместимость.
9. Сообщает пользователю фактический результат, оставшиеся ограничения и нужные решения.

### Исполнитель

1. Читает карточку, актуальные правила проекта и относящиеся к задаче решения.
2. Работает только в выделенной рабочей копии и ветке.
3. Соблюдает область задачи и оговорённые контракты.
4. Реализует изменения, относящиеся к ним тесты, миграции и документацию.
5. Запускает требуемые локальные проверки и сохраняет точные результаты.
6. Сообщает о блокировках сразу, а не маскирует их обходными решениями.
7. Передаёт результат оркестратору в согласованном формате.
8. Не сливает свою ветку в `main`, не изменяет чужие ветки и не публикует изменения самостоятельно.

## 4. Рабочий цикл

```text
Опрос → спецификация и критерии → разбиение и контракты
     → изолированная реализация с тестами → проверка оркестратором
     → исправления при необходимости → интеграция → проверка общего результата
```

### Перед реализацией

- Закрыть вопросы, от которых зависит задача.
- Зафиксировать наблюдаемое поведение: вход, успешный результат, ошибки и права доступа.
- Для изменения данных определить инварианты, транзакции и требуемые миграции.
- Для конкурентных действий описать, что должно произойти при одновременных запросах.
- Для внешнего сервиса разделить тест адаптера с подменой ответа и отдельную проверку реального подключения. Нельзя выдавать подмену за работающую интеграцию.
- Для каждого нового поведения сначала написать тест и получить содержательный RED, затем реализовать поведение до GREEN и выполнить REFACTOR. Команда и причина RED/GREEN входят в отчёт. Для bootstrap и документов достаточно относящихся к ним smoke-проверок.

### Параллельность

Параллельно выполняются только задачи с согласованными зависимостями и непересекающейся ответственностью. Число исполнителей ограничивается реально независимой работой и возможностью оркестратора её проверить.

Не требуется отдельный агент на каждый файл. Тесно связанные изменения выгоднее объединить в одну задачу или выполнить последовательно.

## 5. Ветки и рабочие копии

### Назначение веток

| Ветка | Назначение |
| --- | --- |
| `main` | Принятая и воспроизводимо работающая версия |
| `integration/<stage>` | Временное объединение связанных задач этапа при необходимости |
| `task/<id>-<slug>` | Одна ограниченная задача одного исполнителя |
| `fix/<id>-<slug>` | Отдельное исправление уже интегрированной ошибки |

Если среда требует собственный префикс веток, он применяется перед этими именами. Названия остаются однозначными и содержат ID задачи.

### Правила изоляции

- Каждая активная задача получает отдельный Git worktree либо отдельный checkout.
- Один worktree и одна ветка имеют одного пишущего исполнителя.
- Оркестратор интегрирует изменения в своей рабочей копии.
- Одновременное переключение веток в общем каталоге запрещено.
- Базовая ветка и точный commit SHA фиксируются в карточке до начала работы.
- Зависимая задача стартует после принятия необходимого контракта или изменения. Работу от непроверенной ветки допускаем только с явным описанием зависимости и планом обновления.
- Текущая подходящая рабочая копия оркестратора используется повторно. Новые worktree создаются для изоляции исполнителей, когда она нужна.
- Создание и удаление worktree выполняются штатными средствами среды. Рабочая копия удаляется или архивируется только после сохранения и принятия результата.

### Коммиты и публикация

- Коммиты содержат связанное изменение и понятное описание.
- До проверки сохраняется точный SHA результата; оркестратор принимает именно его.
- После исправлений указывается новый SHA и повторяются затронутые проверки.
- История общей ветки не переписывается. `reset --hard`, принудительный push и удаление чужих результатов не входят в обычный процесс.
- Удалённые push, PR, публикация и деплой выполняются только при наличии соответствующей инструкции пользователя. Локальная приёмка не требует удалённого репозитория.

## 6. Изоляция окружений и БД

Разные Git-ветки не изолируют PostgreSQL, порты и Docker volumes. Поэтому каждому исполнителю выделяются:

- Своя тестовая БД с уникальным именем, например `taxi_test_t014`.
- Своя локальная конфигурация `DATABASE_URL`, не добавляемая в Git.
- Уникальные порты при одновременном запуске API.
- Уникальное имя Compose-проекта и volumes, если используется отдельный Compose-стек.
- Собственное виртуальное окружение рабочей копии и зависимости из согласованного lockfile.

Можно использовать один локальный сервер PostgreSQL с отдельными базами задач; отдельный сервер для каждого исполнителя не обязателен.

Оркестратор имеет отдельную интеграционную БД. Демонстрационная БД пользователя не используется для тестов и экспериментальных миграций.

Перед миграциями, очисткой тестовых данных и seed исполнитель проверяет, что целевое окружение принадлежит его задаче. Очистка допускается только для явно одноразовых ресурсов задачи. Общие базы и volumes не удаляются.

## 7. Контракты и владение общими файлами

Перед разделением работы оркестратор фиксирует:

- Публичные функции сервисов и схемы данных, необходимые соседним модулям.
- HTTP-маршруты, методы, схемы ответов и основные коды ошибок.
- Сущности, внешние ключи и владельцев изменений схемы БД.
- Разрешённые зависимости между модулями.
- Какие файлы исполнитель может менять и какие требуют координации.

Для текущего mini taxi особое внимание получают контракты предложения водителю и его 30-секундного срока, нормализованный ответ маршрутного клиента, серверный расчёт KZT и различие между открытием Kaspi-ссылки и подтверждением оплаты. Критерии приёмки этих частей должны исключать успешную демонстрацию за счёт фиктивного статуса.

Один назначенный владелец в каждый момент отвечает за общие файлы:

- `pyproject.toml` и `uv.lock`;
- `main.py`, общий API router и обработчики ошибок;
- настройки и подключение к БД;
- Compose, Dockerfile и общие скрипты;
- `alembic/env.py`, общий metadata и порядок ревизий;
- общие тестовые фикстуры и схемы;
- этот документ и `BACKEND_PLAN.md`.

Если исполнителю нужно изменение общего файла или контракта, он передаёт оркестратору причину, предлагаемый diff и затронутых потребителей. Оркестратор согласует изменение и обновляет зависимые задачи. Исполнитель не делает скрытую несовместимую правку.

## 8. Координация миграций

1. Карточка заранее указывает, меняет ли задача схему БД.
2. Оркестратор назначает владельца ревизии и фиксирует исходный `head` Alembic.
3. Создание и интеграция финальных ревизий выполняются последовательно относительно принятой цепочки. Работа над остальным кодом может идти параллельно.
4. Если исходный `head` изменился, исполнитель останавливает передачу миграции и согласует обновление с оркестратором.
5. Ещё не опубликованную и не применённую в общей среде ревизию можно пересоздать на новой основе. Просто изменить `down_revision` без проверки содержания недостаточно.
6. Если обе ветви уже стали общей историей, оркестратор проверяет совместимость и готовит осмысленное объединение ревизий. Применённые ревизии не переписываются.
7. В принятой общей ветке должна быть одна вершина. Наличие одной вершины не заменяет проверку конфликтов схемы и данных.
8. На отдельной БД выполняются установка с нуля и обновление с предыдущей принятой версии; при необходимости — проверка обратимости.

Миграции не запускаются конкурентно на одной БД несколькими исполнителями или экземплярами приложения.

## 9. Карточка задачи

Карточки подготовлены в `docs/tasks/`. Их порядок, зависимости и статусы находятся в `docs/TASKS.md`. Поля фактического SHA, worktree и БД заполняются при старте, когда доступна актуальная основа. Зависимые ветки заранее от устаревшего `main` не создаются.

```markdown
# T-000: Краткое название

Статус: ready
Исполнитель: фактическая модель/сессия
Базовая ветка и SHA:
Рабочая ветка:
Worktree/checkout:
Тестовая БД / Compose project / порты:
Зависимости от задач:

## Цель
Какое наблюдаемое поведение должно появиться или измениться.

## Область изменений
Разрешённые модули и файлы; явно исключённые части.

## Контракты и решения
Схемы, функции, HTTP-ответы, права и бизнес-ограничения.
Ссылки на принятые решения. Нерешённые вопросы, если они есть.

## Данные и миграции
Изменение схемы: да/нет.
Владелец миграции и исходный Alembic head.
Транзакции и значимые конкурентные действия.

## Критерии приёмки
- Проверяемые условия успешного выполнения.
- Существенные ошибочные и запрещённые сценарии.

## Проверки
Точные команды, предпосылки и ожидаемые результаты.
Для изменения поведения — тесты до реализации, ожидаемый RED и подтверждённый GREEN.

## Передача результата
SHA, перечень изменений, результаты проверок и ограничения.
```

Задача не считается готовой к делегированию, если её исполнитель должен самостоятельно придумать важное продуктовое правило или публичный контракт.

## 10. Статусы и блокировки

```text
draft → ready → in_progress → review → accepted → integrated → done
                           ↘ blocked
                 review → changes_requested → in_progress
```

- `draft`: требования или зависимости ещё не определены.
- `ready`: карточка достаточна для реализации, зависимости доступны.
- `in_progress`: работает назначенный исполнитель.
- `blocked`: указан конкретный отсутствующий ответ, контракт или техническая предпосылка.
- `review`: результат передан с SHA и проверками.
- `changes_requested`: оркестратор перечислил необходимые исправления.
- `accepted`: конкретный результат прошёл проверку задачи.
- `integrated`: изменения включены в ветку интеграции или основную ветку.
- `done`: проверки общего результата прошли, документы актуальны.

После снятия блокировки задача возвращается в подходящий статус с кратким пояснением. Статусы относятся к карточкам проекта и не подменяют внутренние статусы какого-либо инструмента.

Сообщение о блокировке содержит: что препятствует работе, что уже проверено, какое решение нужно и какая независимая работа ещё возможна. Исполнитель не ждёт молча и не расширяет инфраструктуру как обход проблемы.

## 11. Формат передачи результата

Исполнитель передаёт:

1. ID задачи, ветку, базовый SHA и итоговый SHA.
2. Что изменилось с точки зрения поведения.
3. Перечень затронутых файлов и публичных контрактов.
4. Сведения о миграциях и seed, если они менялись.
5. Точные команды проверок, их результат и использованное тестовое окружение без секретов.
6. Какие критерии подтверждены и каким способом.
7. Известные ограничения и невыполненные проверки с причиной.
8. Подтверждение test-first: тест/команда, содержательный RED и GREEN, либо причина неприменимости к bootstrap/документам.

Нельзя выдавать написанные, но не запущенные тесты за прошедшие. При необходимости прикладывается короткий релевантный вывод; большие логи не пересылаются без причины.

## 12. Проверка и интеграция

### Проверка оркестратором

- Сверить diff с карточкой: нет ли пропущенных требований и посторонней работы.
- Проверить права доступа, транзакции, ошибки, ограничения данных и изменения контрактов.
- Оценить, проверяют ли тесты требуемое поведение и существенные конфликты.
- Проверить отсутствие секретов и нежелательных побочных эффектов импорта/запуска.
- На переданном SHA воспроизвести необходимые проверки задачи; отдельно проверить критичные сценарии, где одного отчёта исполнителя недостаточно.
- При замечаниях вернуть исполнителю конкретную проблему, ожидаемое поведение и критерий повторной проверки.

### Интеграция

1. Сохранить текущую принятую основу и убедиться, что рабочая копия оркестратора не содержит несвязанных изменений.
2. Интегрировать принятую задачу в порядке зависимостей. Для нескольких связанных задач использовать временную integration-ветку.
3. По умолчанию сохранять историю задачи обычным merge. Другой способ выбирается явно; одну и ту же задачу не переносить повторно одновременно через merge и cherry-pick.
4. Конфликты разрешать по смыслу контрактов и схемы. При неоднозначности возвращать вопрос владельцу изменения.
5. На итоговом дереве повторить проверки, которые могли затронуть интеграция, обновление основы или разрешение конфликтов.
6. Перед переносом завершённого этапа в `main` выполнить локальный линтинг, типизацию, полный релевантный набор тестов и проверки миграций при изменении схемы.
7. Проверить сквозной сценарий, если этап меняет жизненный цикл поездки.
8. В обычном режиме перенести проверенный результат в `main`. В автономном проходе Claude оставить его в `integration/backend-mvp` для итогового ревью Astra. Обновить карточки, документацию и итоговый SHA.
9. После подтверждения сохранности результата освободить worktree и одноразовые ресурсы задачи.

При ошибке интеграции сохраняется последняя рабочая версия. Исправление делается отдельным изменением либо осмысленным revert с учётом состояния БД. Откат Git-коммита сам по себе не откатывает миграцию и пользовательские данные.

## 13. Локальные проверки вместо CI

Автоматизация допускается в локальных скриптах. CI и сервер проверки не требуются.

Минимум для обычной задачи после настройки проекта:

```bash
uv run python scripts/lint.py
uv run mypy backend/taxi_service
uv run pytest <относящиеся-к-задаче-тесты>
```

При изменении БД дополнительно проверяются история Alembic, обновление тестовой схемы, `alembic check` и соответствующие тесты миграций.

Оркестратор назначает проверки по реальному риску изменения. Уже прошедшие неизменившиеся проверки не повторяются без причины; обновление основы, новый код и разрешение конфликтов являются причиной проверить затронутую интеграцию.
